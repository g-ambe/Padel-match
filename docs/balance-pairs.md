# バランスペアの評価・選択改善

基準main：`8a324c95403bfc44db098696a80439a5302ba14e`（PR #165）。変更はバランスペアの評価、同一グループの過去戦績の読み取り、直接必要なテストに限定する。

## 原因と変更範囲

以前は全モード共通で、過去ペア1回につき800、未経験相手がいる場合4000、直前ペア5000を加算し、最良ペア評価＋400以内だけを残していた。残った候補では対戦重複評価が優先され、バランス固有値の重みは0.6だった。強弱ペアを評価する前に候補がほぼ固定されていた。

バランスペアだけを別の選択経路へ分ける。通常・ライバルの候補生成、ペナルティ、枝刈り、乱数消費を変えない。当日の好調度の式を共通関数に取り出したが、演算は同一である。解放条件は当該イベントの成立済み・保存済み10試合のまま。過去戦績は解放へ加算せず、選択保持方法も変えない。

## 強さ評価

当日と過去を別々に、既存の好調度の式で計算する。nは試合数、wは勝数、dは引分数、diffは得失点差。

`F = clamp(100 × (w + 0.5 × d + 2) / (n + 4) + 2 × clamp(diff / n, -4, 4), 0, 100)`

n=0の当日評価は50。勝敗・引分は保存スコアの大小を使い、順位やプロフィールのレベルから推定しない。勝率の中立値補正と平均得失点差の制限を維持する。

- 当日出場済みで対象となる過去戦績のあるメンバー：`0.8 × F当日 + 0.2 × F過去`
- ゲスト、過去戦績のないメンバー、永続選手IDがない参加者：当日100%
- 当日の有効な出場がまだない選手：50。過去の実績だけで高低を決めない
- 0-0等の保存済み引分は未出場とは区別し、試合数に含める

過去1勝・4点差の評価は68に補正される。当日50と混ぜても53.6で、少数試合の生の100%勝率をそのまま使わない。比率選択UIは追加しない。

## 過去戦績の対象・権限

過去履歴はバランスペアの生成時だけ読む。現在のイベントをDBから再取得したグループID・作成日時で絞り、既存の `fetchCountedFriendlyEvents` に任意の限定条件を追加して使う。従来の戦績画面の呼出し・定義は変えない。

対象は同一グループ、現在イベントと別ID、現在イベントより作成日時が前、終了済み、未削除、`stats_mode = official`、通常フレンドリーの自動／手動イベント。試合の作成日時も現在イベントより前に限定する。チーム戦・公式戦のテーブルは読まず、別グループ・開催中・削除・記録用・未決定・未来／同時刻のイベントは除外する。

既存の `getHistoricalGroupMatchTeams` と `hasEnteredFriendlyMatchScore` を利用し、当時の所属履歴にあるメンバー4人の成立済み試合だけを数える。現在の退会状態で過去の試合を落とさない。ゲスト混在、未確定、不正得点、不足・重複する選手、別イベントの参加者を混ぜた試合は除外する。通常試合には個別の論理削除列がなく、物理削除された試合は取得に現れない。

対応付けは `event_participants.player_profile_id` のみ。表示名、認証ID、別イベントの参加者IDで同一人物を推定しない。統合済みプロフィールは既に移管された参照先IDを使い、異なるIDを勝手に再統合しない。旧 `profile_id` は既存の所属権限確認には使うが、過去戦績との人物照合には使わない。

本人の既存セッションで、有効な同一グループ所属またはsuper_userを確認してから対象履歴を読む。取得列はID・区分・得点等に限定し、選手名・メール・認証IDを履歴として返さない。過去イベント取得は常にグループIDで、参加者・試合取得は許可されたイベントID集合で絞る。追加のサーバー代理取得や管理用キー、RPCはない。

ページング・100件ずつのID分割は既存ヘルパーを利用する。履歴0件は当日100%へ戻せるが、認証・所属・通信・RLS・途中ページの取得失敗はエラーにし、Round保存前に停止する。通常へ自動切替したり、取得できた一部だけを黙って使用したりしない。

同一試合に同一得点の結果が複数ある場合は、既存集計と同じく1試合を1回だけ数える。対象試合に異なる得点が複数あれば、先頭・最新を勝手に選ばず停止する。DBの重複行は変更しない。

既存の広いRLSは今回修正していない。画面側の所属確認はDBの完全なアクセス制御を保証するものではない。新しい権限付与・更新経路・他グループの情報表示を追加せず、RLS改修は別作業とする。

## 選択処理

休憩者は変更前と同じ600回探索・重み・乱数で先に選ぶ。好調度・モード・過去評価は休憩選択へ渡さない。

出場者が決まったら、最大20人の部分集合DPでペアを決める。評価を一つの大きな重み付き和にせず、以下のベクトルを左から順に最小化する。

1. 直前Roundと同じペア数
2. ペア内の強さの差の合計にマイナスを付けた値（強弱を組ませる）
3. 各ペアの合計強度と出場者全体の平均ペア強度の差の二乗和
4. 過去のペア回数に対する `log(1 + 回数)` の合計

直前ペアを避けられない場合も全候補中の最少数で生成する。実際の直前Roundのペアだけを数え、休憩前のペアを単純に2連続扱いしない。2Round以上前のペアは許容し、未経験ペアの強制や最良＋400の制限は使わない。過去回数は上位の強弱・バランスが同じ場合の軽い減点として働く。

次に、選んだ最大10ペア同士の対戦を別の部分集合DPで決める。

1. 対戦するペア平均強度の差の合計
2. 直前の相手2人ともと再戦する選手数
3. 過去の対戦回数の合計

相手1人だけの連続重複には追加減点しない。コート番号の割当は従来どおり乱数で偏りを避ける。ペア構成と対戦は2段階で選択し、選んだペア群の中では対戦差を最小化する。全試合で接戦になることを保証する評価ではない。

バランスペアの診断値 `pair` は過去ペアの軽い減点、`opponent` は相手2人ともとの再戦人数に変わる。`modePenalty` と `final` は比較用の共通バランス評価で、選択は診断の `priority` ベクトルを使う。通常・ライバルの診断値・選択式は変更しない。

## 同一条件・128シードの比較

参考イベント「テスト261029」を2026年10月30日07:35:00（日本時間）に読み取り専用で確認した。10人（メンバー9・ゲスト1）、2面、Round1〜11、21試合すべて有効スコアあり。前回の18試合から増えているため、以下は新しい固定スナップショットでの比較である。この作業から本番の生成・保存は行っていない。

同一グループの対象過去イベントは5件、取得した過去試合は66件。既存の正式なメンバー戦績対象は25試合で、9人に過去評価があった。対象25試合のうち23試合で同一得点の結果行が重複していたが、異なる得点の重複は0件だった。1試合1回で評価し、過去データ自体は修復していない。

氏名・認証ID・グループID・永続IDを除外した [固定履歴](../tests/fixtures/balance-event-261029.json) を利用する。同じ参加者・当日履歴・過去履歴・面数・Mulberry32 seed 1〜128で、各回を独立に生成し、生成結果を次の履歴へ追加しない。

再現：`node scripts/analyze-balance-pairs.cjs`（ローカルのみ）。変更前の生成器はPR #165の [凍結ソース](../tests/fixtures/friendly-rounds-before-balance.ts.txt)。元の当日100%版に加え、好調度の入力だけを同じ80:20にした対照実験でも旧枝刈り・候補選択・重みを維持する。

全行の強さに関する比較指標は共通の80:20評価で計算する。「旧選択＋80:20」は過去評価が旧製品にも存在したという意味ではなく、比率と候補選択の効果を分けた比較用の処理である。

当日100%でも改善するが、今回の共通評価では80:20の方が対戦差が小さい。1グループの固定履歴だけで比率の普遍的な最適性は断定しない。古いペアと一部の相手の再登場が増えることは、今回許容されたトレードオフである。実際の試合が接戦になったかは未検証。
