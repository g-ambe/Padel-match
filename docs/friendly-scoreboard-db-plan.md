# フレンドリーのスコアボードと生成後メンバー変更

## このPRのリリース判断

**自動マージ不可。ログインイベントのメンバー変更は未実装・無効のまま。** UI改善とゲスト編集をレビューできるDraftとする。新しいMigration・RPC・本番SQLは追加・適用しない。ログインイベントの原子的保存とスコア競合対策が必要であり、ユーザー指定のマージ停止条件に該当する。

## UIの変更

- 開催名・状態と3タブの下に最新Roundの2面を表示する。3〜5面は残りコートを展開できる。各コートは非表示時もマウントし、全コートの未保存状態を生成・終了ガードへ渡す。
- ペアA/Bを緑・青の面と境界線で区別する。数字から既存ScoreInputを開く。名前を省略した場合は数字から開いた入力画面の名前欄をスクロールして全文を確認できる。
- 最新カード→生成ボタン→組み合わせ・コート数→固定ペア→過去Round・全履歴→YouTube一覧・管理→終了の順とする。設定・履歴・動画の折りたたみ内もマウントを保持する。
- タブは下線と文字色で選択を示し、矢印・Home・End、ARIA、入力保持を維持する。保存中・失敗はカードと対戦タブの小バッジで示す。大きな誘導枠とスコア保存成功メッセージを削除する。
- 参加／手動休憩のワンタップを維持する。新たな欠席設定メニューを非表示とし、既存absentは欠席と表示して「参加に戻す」を残す。状態更新のCAS・更新1件・再取得・連打防止は維持する。
- 結果・順位・MVP・戦績反映条件、認証・プロフィール、チーム戦・公式戦の詳細、ScoreSaveProviderと保存キューを変更しない。共通ScoreInputとYouTube表示のコンパクト化はオプションで、他形式のデフォルト表示を維持する。

## ゲスト編集の実装範囲

1. 開催中・自動生成・未入力カードで「メンバー変更」を選ぶ。
2. 選手→入れ替え相手を選び、同コート・別コート・当該Roundの自動休憩者との変更を編成する。手動resting・absentは入替先に含めない。
3. 保存前は元カードを変更しない。保存時にイベント全体のスナップショットを再照合し、終了・参加状態・スコア・別編集・次Round生成との競合を拒否する。
4. 同一Roundの全カードで、4名・各ペア2名・選手重複なし・有効参加者・変更対象のスコア未入力を検査する。結果行が残る未完了カードも変更しない。
5. 既存のゲスト保存処理を使い、Round全体を1回の同期sessionStorage書込みで確定する。match ID・日時・URL・他Round・得点・参加状態は保持する。保存後に照合する。

Storageの書込み拒否では元の値を保持する。書込み後の確認に失敗した場合は成功扱いせず、確認できない結果を自動で巻き戻さない。保存結果は両コートとも旧状態または両コートとも新状態であり、片側だけの書込みは行わない。同一タブの一時イベントが対象であり、サーバー上の複数端末トランザクションを検証したことにはしない。

編集を開いている間は既存boardOperationで生成・終了・固定設定等と排他し、スコア入力も止める。既にキューにある保存は編集開始を拒否する。保存後も変更済みカードを保持し、従来のランダム生成で次Roundを追加する。既存のゲスト生成は履歴を参照しないため、編集後の出場・休憩履歴を次Roundの選考へ反映することは未対応。アルゴリズムを無断で変えない。ゲストは既存仕様で固定ペアの対象外。

## ログインイベントで流用できない既存処理

- `app/events/[id]/page.tsx` の `saveLineupEdit` は `match_players` のDELETEとINSERTを別リクエストで行う。通信失敗・別コートとの同時編集を一括で戻せない。自動生成Roundへ流用しない。既存の手動機能は今回変更しない。
- `0040_event_fixed_pairs.sql` のRPCは取得・固定設定・新規Round生成・終了／再開であり、既存Round編集はない。`guard_legacy_write` は固定設定あり／利用済みイベントへの通常の行追加・team更新を拒否する。
- 既存のID保護トリガーも `match_players.participant_id` のクライアント直接変更を拒否する。権限やトリガーを緩めて回避しない。
- `lineup-db-boundary.test.cjs` は既存スキーマ・適用記録を隔離PostgreSQL互換環境へ再現し、直接更新の拒否と、削除後の再登録失敗をROLLBACKして行を保持できることを実SQLで確認する。これは新規編集RPCの安全性・本番の現行ポリシー一致・実PostgreSQLの同時接続試験を完了したことを意味しない。

## 別作業で必要なDB設計

### 原子的なRound編集RPC

- 公開RPCは認証ユーザーだけに限定し、呼出者の現行の開催操作権限（一般メンバーを含む既存条件・グループなし作成者・super_user）をDBで検査する。SECURITY DEFINERは固定search_pathと完全修飾名を使い、PUBLIC・anonへ実行権限を与えない。
- イベント→Round→対象matches→match_players→参加状態の順を既存0040と整合させてロックする。対象は同一イベント・同一Roundに限る。スコア済み・終了済み・無効参加者をDBで拒否する。
- 編集開始時の全カードの行ID・選手・チーム・結果状態、または同等のリビジョンを受け取り、ロック後にCAS照合する。単にブラウザで確認してからUPDATEしない。
- 両コートを同一トランザクションで変更し、ID・試合日時・動画・得点を維持する。必要な既存行だけを更新し、全体の一意出場・4名・2対2を再検査する。途中例外は全体ROLLBACKする。
- 操作UUIDとペイロードを監査し、応答喪失後の同一リクエスト再送は既存結果を返す。別ペイロードによるUUID再利用は拒否する。変更前後・実行者・時刻・対象Roundを保存する。

### スコア保存との競合はロックだけで解消しない

メンバー変更が先にコミットし、古い対戦カードを見ていた別端末がその後にスコアINSERTする順序も成立する。既存 `saveScore` は選手構成の期待値をDBへ渡さないため、matchesのロックだけでは古い選手のスコアか判別できない。

スコア保存側にも期待する構成／リビジョンを渡し、同じ排他順序で照合する原子的な保存手段が必要。ScoreSaveProviderと再試行キューは維持し、書込みアダプターだけを対応させる方針を検討する。旧クライアントの直接INSERT／UPDATE経路をどう閉じるか、再試行中の旧クライアント・デプロイ前後の互換性も確認する。単なるクライアント再取得を整合性保証として扱わない。

### 固定ペア・公平性の履歴

固定設定、`event_fixed_pair_rounds`等の実使用・参加可能者・出場者・分割履歴、次Roundの履歴計算を同時に照合する。固定ペアの両者が出場する場合の同一チーム条件を維持し、固定の削除や利用済みフラグの消去で整合を取らない。履歴を安全に更新・監査できる設計が確定するまでは、固定使用済みRoundの編集を禁止する。

### リリース前に必要な作業

1. 本番の最新スキーマ・RLS・GRANT・トリガー・RPCを読み取りで照合する。
2. UIとは分離した追加Migration、事前調査、DB外バックアップ・復元確認、適用後検証、復旧手順をレビューする。既存Migrationを書き換えない。
3. 実PostgreSQLの複数接続で、両コート入替、編集同士、スコア先行／編集先行、終了・参加状態変更・生成との競合、応答喪失・再送を試験する。権限の否定ケースと監査も確認する。
4. 手動SQL適用とアプリ反映の順序・旧クライアント対応を承認してから適用する。本PRからSQL実行・マージ・本番デプロイをしない。
