# PR #180：通常フレンドリーのUI先行リリース

対象は自動・手動の通常フレンドリー開催詳細。メンバー入替を分離し、UI整理とスコア入力の重複描画防止だけをリリースする。DB変更・Migration・本番SQL・手動デプロイは不要。

## 残すUI

- コンパクトな開催名・状態、下線型の「対戦／参加者／結果」
- 最新Roundの2コート、次Round生成、組み合わせ・コート数、固定ペア、過去Round、動画一覧・管理、終了の順
- 3〜5面は残りのコートを展開する。非表示のコートも保存キューと生成・終了ガードの対象
- ペアAを緑、Bを青で区別。数字タップから既存ScoreInputを開く。長い名前の全文は入力画面で確認
- 保存成功の大きな通知を省き、カード内のエラー・再試行と対戦タブの小さな保存状態を維持
- 参加／休憩はワンタップ。既存absentの表示・参加復帰・更新確認を維持
- 固定ペア・動画・履歴の折りたたみと、既存の手動Round作成・組み合わせ編集

ゲスト入替UI・保存処理・ログインイベントの無効な変更ボタン・準備中説明・専用テストは今回のランタイムから外す。[次PR用引継ぎ](member-lineup-handover.md)に試作コミットと設計・試験計画を保存した。

## スコア入力を1試合1つにする

通常表示は最新Roundを上部、過去Roundだけを履歴に表示する。「全試合を拡大」では最新を含めて全試合を表示する。

`components/friendly-match-cards.tsx` はmatchIdごとに固定のPortalコンテナを1つだけ作る。通常表示・拡大表示でそのコンテナの配置先を移し、ScoreInput・動画のdetails・手動編成入力を再生成しない。拡大用の第二の入力一覧は作らない。新Round生成時に最新カードが過去へ移る際も同じコンテナを利用する。

ScoreSaveProvider・保存キューとScoreInputの開始・数字選択・確定・取消は変更しない。保存中・失敗はタブを切り替えても表示し、同一のキューから再試行する。チーム戦・オフィシャル戦の詳細UI・履歴コンポーネントは今回変更しない。

## GitHub・Cloudflareの判定根拠

ユーザー提供のPR元コミットのステージングログでは、Next.jsビルド・型チェック・静的ページ生成に成功した後、設定済みデプロイコマンド `npx wrangler preview` が `previews` ブロック不足で失敗した。mainにも同じ失敗チェックが存在し、今回のPRではWrangler・OpenNext・依存関係・Workflowを変更していない。設定不足による既存のステージング問題として別途扱い、今回その設定は変更しない。

マージ可否は最終headのチェックを再取得して判断する。必須チェック・ブランチルールを迂回せず、mainへの反映後は既存の本番自動デプロイを利用する。

マージ前main：`c7519efa9104f2caa5516184757d68d359d2da2c`。同コミットのCloudflare本番成功チェックが記録するWorkerバージョン：`c06a238c-bdf5-45fe-ab44-c8cc4da59af9`。管理APIで現在の配信割合を直接確認した値ではない。

切り戻しは、既存CloudflareダッシュボードのDeploymentsから直前の正常バージョンへロールバックするか、今回のSquashマージコミットをRevertして既存の本番自動デプロイを利用する。管理権限がない環境から推測で操作しない。今回DB変更はないためSQLの切り戻しは不要。
