# フレンドリーチーム戦：選手選択・出欠の設計と適用前確認

## リリース状態

出欠の永続化には0044が必要。現行スキーマにはチーム別の出欠保存先がない。
本PRは本番SQL未適用のためDraftで停止する。DB設計の確認・適用承認後に検証済みSQLを適用し、マージする。
0044未適用でアプリだけ公開しない。取得失敗時は新しい編成を保存できない設計。

## 現行データとの関係

- 通常戦のevent_participants.status（active/resting/absent）は変更しない。
- club_members.status/is_activeはグループ在籍の情報であり、開催の欠席として使わない。
- event_team_guestsに出欠列はなく、ゲストはチーム別。表示名だけでは同名者を識別できない。
- 新テーブルevent_team_attendanceは開催・A/B・所属IDまたはゲストIDをキーとし、active/absentのみを保持する。
- 新しい出欠操作以前のデータには参加を表示する。既存カード・所属・ゲスト・選手を自動変更しない。
- 出欠を参照中の所属・ゲストの物理削除はFKで拒否する。従来の所属状態変更による退会・復帰は維持する。
- member_idはclub_members.idを参照する。player_profilesへの新FKは増やさず、プロフィール統合で所属IDが維持される仕組みに合わせる。
- 出欠はRPCのみで更新。既存の開催作成者・チーム管理者・super_user条件を使う。匿名・一般メンバーは更新できない。
- 未完了カードに含まれる人の欠席化はDBで拒否。完了済みカードは履歴を維持し、スコア・動画・メモのみの更新は妨げない。
- 新しい編成では保存直前にも出欠を再取得する。DBトリガーでも欠席を拒否するため、旧クライアントにも適用される。
- 出欠RPCと編成保存は同じevents行をロックする。READ COMMITTED以外は変更を拒否する。
- トリガーは直接クライアント書込みを検査し、既存の権限を持つSECURITY DEFINERによるプロフィール参照統合等には干渉させない。
- 所属グループはUIで表示専用。名前保存にclub_idを送らない。DBでもクライアントによる開催・side・club_id変更を拒否する。

## UIと既存条件

チームは1人1行で参加/欠席を表示。候補をチーム別のタップ一覧にし、各2名まで選択。
ゲストは既存event_team_guestsの登録処理を利用し、展開時だけ入力する。
既存の自由入力は折りたたみに残す。表示名から別人を自動推定しないため、自由入力だけでは人物の同一性を検証できない。
新規カードの選手未設定時の明示保存・4名設定後の初回スコア自動保存条件は既存どおり。
同一試合のScoreInputは1つ。タブ・全件表示でも入力を保持する。
共有ScoreInputへの追加は表示用pairLabelsだけで、未指定の通常戦・公式戦は表示も保存処理も従来どおり。

## 適用順序（本作業では本番適用しない）

1. 01_preflight.sqlで現行RLS・テーブル有無・件数・プロフィール統合互換性を確認する。
2. [既存バックアップ手順](../supabase/maintenance/event-fixed-pairs/README.md)に従い、暗号化したDB外論理バックアップを取得・保管し、隔離DBへの復元を確認する。秘密情報とダンプはGitへ追加しない。
3. 復元先に0044を試験適用し、02_verify.sqlと専用テストを実施する。既存カード件数・スコア・所属・ゲストのスナップショットを前後比較する。
4. 出欠追加と旧クライアントへの編成制限を確認・承認する。実PostgreSQLで出欠/編成の同時接続試験を再実施する。
5. 承認後、0044だけをトランザクションで適用。02_verify.sqlの結果と既存データ不変を確認する。
6. PRをマージしてCloudflare自動反映を確認し、専用のテスト開催で操作する。実際の試合で破壊的試験を行わない。

## 復旧

アプリは旧Workerへ戻す。0044は基本的に残せる（出欠に反する新規編成は引き続き拒否）。
DBも戻す必要がある場合は、追加後の出欠データを含むDB外バックアップを別途保存し、隔離環境で03_rollback.sqlをリハーサルする。
03_rollback.sqlは既定ROLLBACK。COMMITへ変更するのは対象確認・承認後のみ。
ロールバックは新しい出欠情報を失うため、承認なしに実施しない。既存カード・戦績を削除するSQLは含まない。
