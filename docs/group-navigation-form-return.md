# グループ導線・マイページ・試合作成への復帰

## 今回の画面変更

- 下部ナビを「試合／ランキング／マイページ」とする。アイコン、選択状態、スコア保存中の移動制御、集中操作時の非表示、セーフエリア制御は維持する。
- `/profile` は既存のプレイヤープロフィール編集・戦績・連携申請を残し、独立した「所属グループ」と関連アクションを表示する。先頭の「所属グループへ」から同じページ内の所属セクションへ移動できる。
- 所属一覧は既存 `/groups` の取得条件を `lib/member-groups.ts` へ移して共用する。一般メンバーと管理者の所属条件、旧 `profile_id` のフォールバックを維持し、super_userの全グループ閲覧権限を本人の所属と混同しない。取得エラーは未所属と区別する。
- 試合トップの選択欄付近から `/groups` を開ける。選択グループはユーザー別のsessionStorageに保存し、戻った際に現在の閲覧可能な候補へ照合する。候補から外れた場合は「すべて」へ戻す。
- 通常・フレンドリーチーム・オフィシャルチームの作成画面に、認証済みユーザー向けの「＋ 新しいグループを作成」を追加する。
- ゲストの直接アクセス `/groups/new` では作成フォームを表示せず、既存のメール登録 `/login?mode=signup`、ログイン `/login`、試合トップ `/home` を案内する。

## フォーム復帰

1. ボタン操作時に現在の認証ユーザーを再確認する。
2. 入力値と変更対象をsessionStorageへ保存し、保存内容を確認できた場合だけ `/groups/new?fromMatch=<UUID>` へ移動する。保存不可・容量超過ではフォームに留まり、日本語で案内する。連打による複数の復帰処理を防ぐ。
3. グループ作成は既存のプロフィール確認、`clubs` 作成、`club_members` へのメイン管理者登録を利用する。
4. グループと管理者登録の両方が成功した場合だけ「作成済みのグループID」を復帰情報へ記録する。管理者登録失敗では自動選択しない。グループが既に作成された場合は再作成ボタンを無効にする。
5. 元のフォームを開き直し、従来の取得処理で最新の選択候補を取得してから入力を復元する。作成したグループが候補にある場合だけ自動選択する。候補になければ元の入力を復元し、所属・管理権限や取得状態の確認を案内する。
6. 復元した一時情報は削除する。イベントは送信ボタンを押すまで作成しない。

通常は開催名、コート数、自動／手動、選択グループを保持する。フレンドリーチーム戦は開催名・説明・メモ、A/Bの入力モード・グループ・名称を保持する。オフィシャルはタイトル、グループ、開催日、説明、メモを保持する。

A側のボタンはA側だけ、B側のボタンはB側だけを新グループへ変更する。チーム名や他方の設定は変更しない。キャンセルとグループ作成前のブラウザバックでは元の選択を保持して入力を復元する。

## 保存範囲・破棄条件

- 同じブラウザタブのsessionStorageを使い、認証ユーザーID、形式、UUIDトークンで分離する。入力値をURLへ載せない。
- 戻り先は通常 `/events/new`、チーム `/team-matches/new`、公式 `/official-matches/new` の固定マップから生成する。任意の戻り先URLは受け付けない。
- データ形式、所有者、形式、変更対象、状態、期限を検証し、別アカウントや別形式のデータは復元しない。
- 有効期限は2時間。復元済み、試合作成完了、期限切れの一時情報を破棄する。同一形式はタブ・ユーザーごとに1つのグループ作成往復を保持する。
- 認証済みフォームの保存はグループ作成への往復が対象。復元後は通常の画面内状態へ戻り、再読み込みによる繰り返し復元は行わない。
- 保存を無効にしたブラウザや容量不足では移動を止める。入力は切り詰めない。非常に大きな入力は一時保存対象外として画面で案内する。

## ゲスト

グループ作成の導線は認証確認後にだけ表示する。ゲストには無効ボタンも表示しない。案内を見る、ログイン・登録画面を開いて戻る、通常ナビで移動するだけではゲストイベントを削除しない。`goTop()` は呼ばない。

ゲストの通常作成フォームは、グループ登録案内への直接移動でも入力を失わないよう別領域へ一時保存する。案内表示では破棄せず、試合作成成功または既存の明示的なゲスト終了時に破棄する。実際にログイン・登録して認証済みになった場合は、既存のゲストデータ消去に合わせてゲスト用下書きも破棄する。認証方式は追加しない。

表示判定は認証・DB権限の代替ではない。書込み直前の既存getUser確認、プロフィール確認、DB権限は維持する。DB・Migration・RLS・RPCの変更はなく、手動SQLは不要。

```bash
npm test
npx tsc --noEmit --incremental false
WRANGLER_LOG_PATH=/tmp/padel-group-flow-wrangler.log \
NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321 \
NEXT_PUBLIC_SUPABASE_ANON_KEY=local-test-key npm run cf

# 別のターミナルで実行。Playwright・Chromiumが必要。
node tests/browser/group-navigation-return.cjs
node tests/browser/match-navigation.cjs
```

ビルドとブラウザ試験は順番に実行する。モック用の公開設定を本番環境へ登録しない。

単体試験はユーザー分離、3形式の全入力、A/B、取消・戻る、期限切れ、改ざん・外部URL、容量不足、所属条件・旧列・super_userを確認する。ブラウザ試験は架空データだけを使い、3形式の保存・復帰、権限候補外、管理者所属登録失敗、未所属、ゲスト案内とデータ保持、ゲストのRound生成・スコア・結果、320/375/390px、既存ナビ・保存キューを確認する。本番通信は遮断する。

実iPhone/Safariと本番アカウント・本番RLSでの操作は未検証。PR②の通常開催3タブ化、本番SQL適用、マージ、本番デプロイは今回に含めない。
