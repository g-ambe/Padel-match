# 規約ページとアカウント作成時の同意

`/terms` と `/privacy` はログイン不要の全文ページ。制定日は両方とも2026年10月26日、バージョンは1.0。

## 文書と導線

- `lib/legal-documents.ts` に、提示された利用規約17条・プライバシーポリシー13条を全文・定数として保存する。
- `components/legal-document.tsx` を全文ページと確認ポップアップで共用し、メールアドレスはメールリンクにする。
- 登録フォーム内の規約リンクは、対象文書のタブでポップアップを開く。リンクのクリック自体では同意チェックを変更しない。
- ログイン画面の下部とログイン後のメニューから、両方の全文ページへ進める。閲覧時に認証状態を変更しない。

## 登録処理

同意は画面を開いた時点ではOFF。メール・表示名・パスワード・確認入力の検証を先に行い、有効な入力で未同意の場合に確認ポップアップを開く。

親フォームとポップアップは同じチェック状態・同じ登録処理を使う。チェック操作の日時を保持し、チェックを外すと日時も解除する。全文を最後までスクロールすることは強制しない。戻る・閉じる・Escape・背景クリックでは登録せず、入力値と明示したチェック状態を維持する。

登録開始前に同期的なrefで実行をロックし、連打やフォーム／ポップアップの同時送信を防ぐ。ポップアップ内の操作は処理中無効。Authが失敗した場合は再試行でき、Auth成功後はプロフィール確認中や遷移前の登録再送も防ぐ。既存のメール確認画面と即時セッション時のプロフィール確認フローへ進む。

Supabase Authへの新規登録に、既存の `display_name` と併せて次を渡す。

| メタデータ | 内容 |
|---|---|
| `terms_version` | 明示的に同意した利用規約の版 `1.0` |
| `privacy_version` | 確認したプライバシーポリシーの版 `1.0` |
| `consented_at` | チェック操作時点のブラウザ日時（ISO形式） |

この情報は通常の `user_metadata` であり、利用者自身が変更できる場合がある。日時も端末の時計に依存するため、信頼できるサーバー側の監査証跡にはならない。また、ブラウザでの登録導線の同意確認であり、外部からのAuth API呼び出しまでサーバー側で強制する仕組みは追加していない。必要になった場合は、サーバー側の同意履歴を別途設計する。今回、新しいテーブルやSQLは追加しない。

既存ユーザーへの同意の書き込み・再同意の強制・ログイン制限は追加しない。

## Googleログイン

`app/page.tsx` の `GOOGLE_LOGIN_VISIBLE = false` でボタンの描画を止める。将来の再開はこの表示フラグで行える。既存のOAuth処理とSupabaseのプロバイダー設定、認証アカウントは変更しない。

Google認証だけを使う既存ユーザーは、非表示期間中はこのボタンからログインできない。運用上の周知や必要な代替導線は別途判断する。メール認証、ゲスト利用、既存セッションは維持する。

## 検証

- 提示本文を共通データから元のMarkdownへ再構築し、全17条／13条・本文・版・日付が完全一致することを確認。
- ブラウザで匿名での全文閲覧、全文ページとポップアップの本文一致、タブ切替、入力検証優先、同意前の登録なし、チェック同期、閉じた後の入力保持、明示同意後の登録を確認。
- 連打とフォーム同時送信でも登録要求が1件になること、失敗時の再試行、メタデータとメール確認画面への遷移を確認。
- 両テーマ、320×430の短い画面を含むモバイル／PC、本文内部スクロール、固定された閉じる／登録操作、フォーカス管理・背景スクロール復元を確認。
- メールログイン、ゲスト利用、認証完了の既存案内、規約のメニュー導線、テーマ切替、ログアウト、即時セッション時のプロフィール保持を確認。

ブラウザ検証はSupabase応答をモックし、実際のアカウント作成・確認メール送信・OAuth設定変更は実施しない。リリース前には実端末で読みやすさを確認し、開発用アカウントでメール到達・メール認証後のログインを確認する。

`npm test`、TypeScriptチェック、`npm run cf:build` を実行する。DB・RLS・依存関係の変更はなく、Supabase SQL Editorでの手動適用は不要。
