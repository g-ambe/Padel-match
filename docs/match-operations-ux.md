# 試合運営画面のUI・UX改善

基準mainは `828571cc13f7ea2f6b3a28bc8f65573861fad925`（PR #163）。変更はスコア保存の表示・状態管理と試合運営の配置に限定する。DBテーブル・カラム・RLS・GRANT・RPC・マイグレーションは変更せず、SQLの手動適用は不要。

## 入力後すぐに閉じる仕組み

初回の数字選択は両側がそろったとき、保存済みスコアの編集・キーボード入力は「完了」の操作で、入力ポップアップを閉じる。DB通信の完了は待たない。片側だけの入力や不正値では送信せず、キャンセルは送信前の値を変更しない。

`ScoreSaveProvider` が画面の外側で、試合ごとの送信状態・入力値・エラーを保持する。試合カードには「保存中…」と「未確定の入力」を表示し、成功応答後だけ既存の保存処理が確定スコア・WIN／LOSE／DRAWを更新する。失敗時は以前の確定値を残し、カード上にエラー・「再試行」を表示する。

同期ロックにより、通常一覧と全件モーダルから同じ試合を同時送信できない。他の試合の閲覧・スクロール・スコア保存は継続できる。再試行では入力を再利用し、PR #163の結果ID・新規カードUUID・書込みロックもイベント単位で再利用する。モーダルを閉じたり、アプリ内で別画面へ移動して戻った場合も保持する。別画面では未保存の案内と戻るリンクを表示する。

古い再取得レスポンスが新しい確定値を上書きしないようイベント単位で保存状態の世代を確認し、古い応答は再取得する。終了・再開の成功応答でも世代を進め、古い表示へ戻さない。保存中・失敗中の試合は以前の確定スコアを維持し、応答を受け取れなかった新規カードを確定済みとして追加表示しない。保存がすべて完了したときに履歴を再取得する。

## 終了・競合操作・画面移動

- 保存中または失敗中のスコアがある場合、次Round生成・終了確定を防ぎ、保存完了または再試行を案内する。終了確認画面を開いて理由を確認できる。
- 終了処理が先に開始した場合も、新しいスコア書込みを開始しない。通常・チーム・公式の3形式でDBリクエスト前に確認する。
- 保存中の同じ試合のスコア編集、カード削除、競合するカード情報・動画更新を抑止する。通常の動画操作は既存のURLだけを更新し、得点を上書きしない。
- 手動試合の組み合わせ編集中は得点入力を止め、スコア未保存中は同じ試合の組み合わせ変更を防ぐ。
- 再読み込み・タブを閉じる操作には、未保存データがある間だけブラウザ標準の警告を出す。ゲストの一時データを消す「TOPへ戻る」も未保存時に抑止する。

入力・再試行状態はタブ内のメモリで保持する。強制終了や警告を無視した再読み込み後まで復元する変更は行っていない。通信を中断してDB書込みを取り消す設計ではない。

## 選手名・ゲスト

通常は既存の参加者IDとチームA／B、チームは4つのプロフィール・ゲスト欄、公式は自選手2名・相手選手名2名を使う。得点ボタンとポップアップの両方に名前を表示し、名前変更によってA／Bの内部対応を変えない。

名前はペアごとに2行で表示し、長い名前は省略する。完全な名前はDOM・読み上げラベルに保持し、省略部分にはtitleも設定する。ゲストタグは省略せず、区分のない公式の相手選手を勝手にゲスト扱いしない。未設定には代替表示を使う。スコアボタンへ名前をまとめ、カード内の重複した選手名の行を削減した。

## 約2試合の一覧・拡大

通常一覧は高さを最大 `min(25rem, 50dvh)` にし、全試合を内部スクロールで確認する。件数が少ない場合は高さを強制しない。カードの高さ・長い名前・画面高によって見える件数は変わる。文字・数字ボタン・タップ領域を極端に小さくしない。

右上の44px以上の拡大アイコンから、画面高の約92%を使う全件モーダルを開く。幅いっぱいの「すべて表示」ボタンは廃止した。×・背景タップ・Escape、モーダル内の得点編集、重ねた入力ポップアップ、フォーカス・背景スクロール・元の操作位置の復元を維持する。

スマホでは上部の専用ハンドルから下方向へ80px超スワイプした場合にも閉じる。横移動が50px以上の操作、履歴や入力エリアから始める操作では閉じない。スクロールや選手入力と競合させない。

## スマホの運営エリアとイベント終了

通常イベントでは、タイトルのすぐ下に「試合運営」を配置した。

1. 現在Round・約2試合の一覧・拡大アイコン
2. 現在選択中のモード。開くと既存の選択肢・解放条件・説明を確認できる
3. 強調した「次Round生成」（手動イベントでは既存の作成フォーム）
4. 枠線の「イベント終了」と「終了後、ランキング・MVP・結果共有を確認できます」の案内

参加者・ゲスト追加・動画管理は下に残し、既存機能を削除しない。モードの選択・保持・生成アルゴリズムは変更しない。

終了確認では、ランキング・MVP・共有の案内、未確定試合の件数、未確定試合が正式な集計に含まれないことを表示する。手動イベントの戦績反映／記録用の選択は維持する。終了成功後は結果サマリーへ移動し、既存の各ランキング・MVP・共有作成／コピー／停止／再発行を使用する。共有リンクは自動発行しない。再開・論理削除は既存の処理を維持する。

## 既存ロジック・データへの影響

基準mainと通常の `generateRound`・`eventSummary`・`getWinnerTeam`・`selectRoundMode`、チームの `teamMatchStats`・`validate`・`autoResult`・`payload`、公式の `officialStats`・`validateMatchForm`・`autoResult`・`matchPayload` がコード一致することを確認した。計算・生成・モード保持・共有用lib、プロフィール連携、イベント削除処理、Supabase関連ファイル、依存関係、Cloudflare設定は変更しない。

通常の結果ID再利用と、チーム・公式の新規UUID再利用は継続する。チーム・公式の未設定選手を含む明示保存は維持し、新規の自動登録はPR #163と同様に全選手設定済みの場合に限定する。PR #161の履歴集計、70／20／10、ペア順位付け、ゲスト混在条件を変更しない。

## 本番反映と切り戻し

ステージングは今回の依頼で利用不可と指定されているため、必須条件にしない。ローカル・モック・ブラウザ検証と差分レビューで判断し、重大な問題がなければ同じPRをReadyにしてSquash mergeする。本番は既存のCloudflare Appのmain連携を使い、手動で二重デプロイしない。

反映前の記録：main `828571cc13f7ea2f6b3a28bc8f65573861fad925`、本番Worker `padel-match`、対応する成功ビルド `8f85d50b-5fc7-40ea-ba07-32720d0badf3`、Version ID `1ac47cff-6adc-4297-92c5-05363b97aa5b`。CloudflareのGitHub Check Runから確認した成功記録で、稼働APIによる現在値はこの環境の認証・通信制限で未確認。

反映後のマージSHA・Worker Version ID・本番動作確認結果はPRの最終コメントに記録する。本番画面とCloudflareのエラーログは可能な範囲で読み取り確認し、実試合の保存・変更・削除テストは行わない。

重大な障害時は、既存の認証済みCloudflare環境で上記の正常版を確認し、Deploymentsのロールバック、または `wrangler rollback 1ac47cff-6adc-4297-92c5-05363b97aa5b --name padel-match --message "試合運営UIの切り戻し"` を使う。コードはSquashマージSHAの `git revert` で戻す。DBデータが自動復元される操作ではない。この環境からの切り戻し実行自体は未検証で、認証情報・設定変更・制限の迂回は行わない。

実端末のOSキーボード・画面操作、実Supabaseでの保存・終了、本番の表示・重大エラーログはローカル検証に含まれない。複数端末をDBトランザクションで排他制御する変更や、既存2リクエスト保存を原子的にするDB変更は行っていない。通常の途中失敗では未確定結果行が残る場合があるが、再試行で同じIDを使う。
