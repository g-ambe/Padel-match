# PR #159の代替・最小セキュリティ対策

main `8f4e1bf` から作成した `codex/minimal-security-replacement` が対象です。PR #159のコミット全体は取り込まず、所属のRLS・親子検査・共有表示・複数行保存・必要なテストだけを選択して再利用しました。旧PRは最終比較後に置換としてクローズする対象ですが、ブランチ・履歴は残します。本番へのSQL・設定・データ変更、mainへのマージ、スーパー管理者の登録は実施していません。

## 構成と公開範囲

閲覧できることと変更できることを分けます。変更権限はDBの所属と役職を使い、user_metadataや公開IDを権限証明に使いません。メイン・サブ・一般という既存の区分は維持します。

| 情報・操作 | 提供する範囲 |
| --- | --- |
| 公開グループ | 名前・概要・画像・施設など。所有者の認証UIDは直接SELECT不可 |
| 公開相当の選手情報 | `public_player_profiles` の選手ID・表示名・画像だけ。表示名の重複可。未連携の仮選手は含めない |
| 仮選手の加入候補 | 公開グループの有効な未連携選手の名前・申請用IDだけ。ログイン必須 |
| グループの名簿 | 所属メンバーが必要な名簿情報を参照。無関係な利用者には非公開の所属・役職を返さない |
| 相手チームの選手 | 正規のチームイベントに関係する利用者へ、選手ID・名前だけを返す |
| 自己紹介・活動地域等 | 本人用取得・保存RPCだけ。グループの他メンバーにも詳細列の直接SELECTは許可しない |
| メール・Auth情報 | テーブルのメールSELECTは禁止。既存の管理者限定・完全一致検索だけを維持。UIのUID先頭8文字表示は廃止 |
| 加入プレビュー | 申請先グループ分だけを返す。別グループの所属名・詳細は返さず、同意の内部JSONも直接SELECT禁止 |
| 通常イベント運営 | 有効な一般メンバーにも作成・Round生成・試合編集・スコア・終了・再開を許可 |
| 過去の本人履歴 | 退会しても本人が参加した終了済み通常イベントと所属概要を参照可。現在の運営権限は復活させない |
| グループ・イベント削除 | APIからの物理DELETE・TRUNCATEを禁止し、既存の論理削除を維持 |
| Round・試合・出場枠 | 直接の構造変更を許可せず、小さなトランザクションRPCで保存する。単一試合の削除を維持 |

現時点ではプロフィール公開設定カラムは存在しません。従来公開されていた有効な連携選手の名前・画像を固定列のビューで提供し、詳細・所属・認証UIDとは分離しています。新しいSNS検索画面や公開設定画面は実装していません。

通常・チーム戦・公式戦の共有は `get_shared_event(p_token,p_kind)` に統一します。匿名・別グループのログイン中でも、有効な終了イベントのURLを表示できます。無効・停止・削除・再開後は表示しません。直接テーブルを使った匿名のトークン列挙は拒否します。所属メンバー・管理者による自グループの共有管理・URLコピーは従来どおりです。

共有には認証UIDや元の選手キーを含めず、必要な選手名・グループ名・結果を返します。チーム・公式の選手集計キーはイベント単位の識別子にし、同名の別選手も別人として集計できます。共有JSONは固定項目だけで、将来追加した私的カラムを自動的に公開しません。

## 戦績・本人承認・保存

現行のイベント・グループ・プロフィール画面は、試合結果を読み出して戦績を算出しています。画面表示に使われていない旧 `player_stats` へのクライアント加減算を止め、旧累計は既存ID・所属・数値のまま保持します。NULL所属も推測して移管しません。

これにより、旧累計の不一致・欠落が新しいスコア保存を停止させません。試合結果は一試合一行のUPSERT、完了状態は同じDBトランザクションのトリガーで保存します。再送・再編集で累計を加算せず、画面は正本の結果を集計します。途中失敗は結果と完了状態を共にロールバックし、日本語でエラーを表示します。既存の重複結果がある場合は一意制約を作成できないため、件数・理由・対応案の確認まで適用を止め、勝手に削除しません。

0039の本人同意、管理者審査、有効期限、確認トークン、役職保護、重複出場・二重所属の検査、統合監査、専用復旧は維持します。旧累計の存在を理由に統合を拒否していた条件だけを外します。旧累計そのものは移動・合算・削除せず、所属・参加者・チーム戦・公式戦など正本の参照を引き継ぎます。試合ID・出場枠・結果を作り直しません。アカウントと選手プロフィールも分離したままです。

旧形式の `profile_id` は認証アカウント、`player_profile_id` は選手として扱います。IDの値が同じだけでは所属を認めず、アカウントからは有効な本人連携先だけを解決します。旧形式の所属も表示・復帰・Round・戦績集計に対応し、格納済みIDは変更しません。連携先がない旧所属は事前点検で件数を確認し、自動補正しません。

既存の `supabase/maintenance/profile-linking/04_restore_reviewed_merge.sql` をそのまま使用できます。統合後の編集を検出したら停止し、監査を保持します。外部ツールが旧累計を現役の数値として使っていないかは未確認で、本番前に確認が必要です。リポジトリ内の表示は旧累計に依存していません。

複数行の保存RPCは、グループ＋初回管理者、チーム＋両サイド、Round＋試合＋枠、未採点の組合せ、単一試合削除の5種です。本人の私的プロフィール更新も限定RPCで扱います。その他の単一行操作はRLS・GRANTと通常のSDK操作を使います。Round算法・公平性・休憩順・ゲーム形式は変更していません。

## 参加者の人物識別保護と旧PRの最終比較（2026-10-28）

従来は変更先のグループ所属が有効なら、通常APIから既存参加者を別人に変更できました。既存の `guard_parentage` トリガーの変更禁止列に `player_profile_id`・`profile_id`・`participant_type` を追加し、一般メンバー・管理者とも拒否します。NULLへの解除やゲストへの種別変更も同じ条件で拒否し、拒否時は人物・出場枠・結果・戦績を変えません。新しい関数・トリガー・RPC・監査機構は追加しません。

状態・ゲスト名の編集、人物IDの同値送信、未採点の組合せ変更、スコア再編集は維持します。組合せは既存の専用RPCで出場枠を変更し、人物IDは変更しません。0039の権限付き承認処理は既存の実行ロール判定で通し、本人同意・統合監査・二重所属／重複出場の検査・専用復旧も維持します。誤った本人申請を管理者が承認する場合の本人確認は運用判断とし、新しい認証要件は追加しません。旧ID形式の試験データはローカルDB所有者で準備し、通常APIでの付け替えに依存しません。

## 適用・切り戻し

本番に対して実行していません。必要な実データ補正対象件数は未照会・不明です。マイグレーション適用・再適用時の既存業務行の変更は0件であることを架空DBの全publicテーブルのハッシュで検証します。

1. [01_preflight.sql](../supabase/maintenance/minimal-security/01_preflight.sql)で現物のRLS・ACL・重複結果・不整合な親子・旧IDを読み取り確認します。必要な補正は対象件数・理由・復旧案を提示し、承認待ちにします。旧累計の不一致は補正も適用の停止も不要です。
2. ステージングの[検証手順](minimal-security-staging.md)とレビューを完了します。PR #159のSQL適用済み環境へは直接重ねず、別途差分を確認します。
3. 適用承認後、DB全体のバックアップと復元可能性を確認します。PITRの利用可否・実復元は未確認です。0039の非公開監査も対象にします。
4. 書込・スキーマ変更を停止し、[02_backup.sql](../supabase/maintenance/minimal-security/02_backup.sql)で今回変更するACL・ポリシー・関数定義・照合ハッシュを取得します。これは適用時のメタデータ控えで、操作ごとの監査ではありません。
5. 今回のマイグレーション1件だけを手動適用し、対応するアプリと揃えます。過去の全SQLの一括db pushは行いません。新RPC・ビュー・列権限が必要なため、DB未適用のプレビューだけでは全画面は動作しません。
6. [03_verify.sql](../supabase/maintenance/minimal-security/03_verify.sql)で行内容不変・機密列・削除権限を確認し、正規操作の試験後に再開します。Advisorはステージングで確認します。
7. 再開前の切り戻しは[04_rollback.sql](../supabase/maintenance/minimal-security/04_rollback.sql)を既定ROLLBACKで予行します。業務行に差分があれば停止します。旧RLSへ戻すとP0が再発するため、公開停止を維持します。再開後は互換DBを保った前進修正、または対象・理由・復旧方法を承認したDB復元を選びます。旧アプリへ戻して旧累計更新を再開することは推奨しません。
