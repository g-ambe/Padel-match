## 見つかった依存関係

- 一般の開催画面・グループ戦績・個人戦績は対象6表を直接参照する。試合結果はmatch_players/match_results、Round番号はroundsの埋込み参照を使う。

- eventsには終了済み・共有ON・未削除を条件としたanon SELECTがあるが、トークンを提示したことまではDBで要求していない。無条件SELECTを除去するだけでは、共有ON開催のAPI一覧取得を防げない。

## 先行するアプリ変更

共有ページの読取りに限り、新しいgetSharedEventClient(token)を使う。リンクのトークンをx-padel-share-tokenヘッダーへ入れ、認証セッションを保持/自動更新/URL検出しない独立クライアントにする。通常アプリのログイン用クライアントを変更せず、ログイン中の閲覧者でも公開共有範囲だけで読む。

対象は共有ページ・小さなクライアント生成関数・通信テストの3ファイル。現行RLSは新ヘッダーを使わないため、アプリを先に反映して共有表示を確認できる。RLS6操作の変更は、その反映確認後にSQL・切り戻し・DB検証を提示して承認を得て行う。

前提確認：実Supabase SDKの通信テスト5項目＋既存の共有名RPCテスト5項目が成功し、TypeScriptチェックも成功。通信テストは保存済みの他アカウントのセッションを読まないこと、別トークン間の分離、実際のHTTPヘッダー、無効リンクを確認した。

Next.js本番ビルドも成功。初回はNext.js設定ファイルへの権限制限で停止し、テレメトリー無効・承認された権限制限外の実行で成功した。OpenNextのCloudflare変換は--skipNextBuildで実行したが、Windows非対応警告後120秒以上進捗がなく、実行セッションを停止した。ローカルCloudflare変換の成功とデプロイ管理画面は未確認。後述のとおり共有ページの実表示はユーザーが確認済み。

共有ページの3ファイルだけをmainベースのcodex/shared-event-token-readへ分離し、[PR #169](https://github.com/g-ambe/Padel-match/pull/169)を作成した。2026-11-02、ユーザーの明示承認後にmainへsquash merge済み（e5752bae7805fd1ca7b4e8ec183e0066d27e68ad）。GitHubでもmerged=trueを確認した。SQL/権限の変更やRLS履歴全体はPRへ含めていない。

## 後続SQLの検討方針（未確定・本番未適用）

- 所属中メンバー、グループなし開催作成者、既存スーパー管理者、チーム開催の閲覧者は維持。
- 共有は、終了済み・共有ON・未削除に加え、提示されたトークンと対象開催の一致を要求する。共有用クライアントはanonなので、ログイン状態による挙動差をなくす。
- 匿名の読取り列も共有画面が必要とする範囲へ絞る案を検証する。イベントの説明/メモ等を、画面に出ないという理由だけで非公開扱いにしない。
- 子テーブルの参照・埋込みまで、親開催の閲覧範囲に合わせる。RLS再帰とNULL/親不整合、一覧・集計の欠落を検証する。
- 2026-11-02ユーザー決定：退会後はそのグループの履歴も見せない。通常アプリの個人戦績・集計では、有効な所属がなくなったグループの過去履歴も対象外とする。過去の出場・作成者という理由だけでグループ開催の閲覧を許可する例外は追加しない。公開された共有リンク経由の閲覧は通常アプリの履歴とは別の既存要件として、提示トークンで判定する。既存のスーパー管理者権限とグループなし開催の本人閲覧は維持する。
- 既存のINSERT/UPDATE/DELETEのUSING/WITH CHECKはSELECTにも依存するため、前セットまでの正常運営を重ねて再検証する。管理者接続だけの確認で完了にしない。
- 匿名で無条件に個人プロフィールを全公開するような追加権限は入れない。公式戦official_eventsの共有は今回の6表とは別で、既存の専用グループ名RPCを維持する。

この段階では本番用SELECT変更SQLを確定していない。先行アプリ変更だけでデータベースの一覧取得制限が完了したとは扱わない。
