# RLS改修の進め方・使用量への配慮

ユーザー指定：利用できる選択肢はSol・中またはAstra・低。各工程で作業と推奨設定を明示し、選べない高モードを必須条件にしない。現在はSol・中で進める。

仕様相談を別のChatGPT、コード/DB調査と検証をCodexに分担してもよい。ただし併用だけで利用枠が節約されるとは保証しない。料金/上限は契約と接続方法に依存し、この作業の正確な消費量・節約率は測定できていない。

- 同じ説明・調査を両方で繰り返さず、引継ぎは対象、決定事項、未確認事項、承認範囲の短い要約にする。
- このトークでは差分を中心に報告し、巨大なSQL/全ログの再出力を避ける。必要な証拠はGit内のファイルを参照する。
- 既知の失敗や不変の全テストを理由なく繰り返さない。関連テストや新しい失敗が必要とする範囲で再検証する。
- 合成DBの過去工程の再実行は、依存状態を再現し新変更との回帰を確認する必要がある場合に行う。モデルへ返すログは末尾の要約に絞る。
- 本番変更は影響の小さいものをまとめるという後続のユーザー指定に従い、同じ画面・テーブルで一緒に確認できる操作はセット化する。承認は省略せず、SQL・切り戻し・一連の実操作への影響を提示する。
