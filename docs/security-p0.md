# PR-A／P0：イベント権限の保護

対象は調査報告のS-01〜S-03と、その修正に必要な共有表示の互換性対応です。利用規約・Round生成アルゴリズムの開発とは分離しています。添付資料は調査資料として参照し、今回の実施範囲・禁止事項はユーザーの依頼を優先します。

本PRから本番SupabaseへSQLを送信したり、設定を変更したりしていません。適用時に選手・所属・試合・戦績の既存行を移行・統合・削除しません。現行の一般メンバーによるイベント運営、個人イベント、共有URL、sessionStorageのゲストモードを維持する方針です。

## 変更する境界

- `clubs`, `events`, `event_participants`, `rounds`, `matches`, `match_players`, `match_results`, `player_stats` の無条件`dev_all_*`を、所有者・有効な所属・役職・イベント状態の判定へ置き換えます。既存の別名ポリシーのOR条件から迂回できないよう、対象表のポリシーをまとめて定義し直します。
- 親イベント・Round・試合・参加者の関係を、新規行にも検証します。所属先や作成者などの変更による権限移動を防止します。既存の0039参照保護と同意・承認フローは保持します。
- チーム所属をイベント権限の根拠に使用するため、`event_team_sides`への偽の所属登録も同じPRで閉じます。チーム戦全体のP1監査は別途必要です。
- 公開共有は「有効なトークンを知る人が閲覧する」仕様です。`share_enabled`だけでイベント一覧を公開しません。公開RPC `get_shared_event(p_token text)`が、完全一致トークン、共有有効、終了済み、未削除、有効な所属グループを確認して表示専用JSONを返します。個人イベントはグループ状態の判定対象外です。
- 共有JSONは必要な表示列を列挙します。認証ID・選手プロフィールID・グループID・イベントID・共有トークンは返しません。参加者の表示対応付けや動画クリックに必要な参加者ID・試合ID・動画リンクIDだけを含めます。既存のクリック計測RPCは維持します。
- 前回本番へ適用済みと資料に記載された、匿名テーブル/列書込の撤回と公式戦の無条件ポリシー3件削除を、冪等SQLへ記録します。

`security_private`はData APIのExposed schemasに含めないことが前提です。内部の読み取り専用SECURITY DEFINERは、トークン境界または固定した本人判定に用途を限定し、空の`search_path`と明示したEXECUTE権限を使用します。ユーザーが編集できる`user_metadata`を認可に使用しません。

## 手動適用と切り戻し

今回は手順とSQLの提出までです。本番適用・設定変更・mainへのマージは行いません。将来の適用は、PRレビュー、ステージングの権限別試験、最新バックアップと復元可能性確認を経て別途判断します。

1. ステージングの実スキーマを本番と比較し、0039の関数・参照保護、共有トークン一意index、必要列・制約・既存ポリシーを確認します。`security_private`がExposed schemasに含まれていないことを、Supabase設定で読み取り確認します。AuthやData APIの設定をこのPRで変更しません。
2. `supabase/maintenance/security-p0/01_preflight.sql`を実行し、資料と現行スキーマの差分をレビューします。初回用preflightは既にP0オブジェクトがある場合に停止するため、再適用時は既存バックアップとSQLを比較します。親子不整合、作成者不明の個人イベント、クラブなし/重複した旧戦績があっても、自動修復しません。
3. SupabaseのDBバックアップ/PITRと外部保管を確保します。P0の運用時刻・実施者・対象ref・アプリコミット・SQLチェックサム・照会結果を適用台帳へ記録します。本番は履歴がリポジトリと一致しないため、過去の全migrationを`db push`で再実行しません。
4. 書き込みを止め、`02_backup.sql`で権限・ポリシー・関数・トリガーの定義と業務行の件数/ハッシュを同一時点で取得します。同名バックアップは上書きしません。このバックアップは権限復旧用で、業務データのコピーやPITRの代用ではありません。
5. P0マイグレーションだけを、レビューしたトランザクション単位で手動適用します。SQL内の前提検査が失敗したら全体が中止されます。8個の旧ポリシーだけを先に手動削除する運用は禁止です。SQL適用とRPCを使うアプリ公開の間は旧共有ページが利用できないため、メンテナンス中に連続して実施します。
6. 書き込みを再開する前に`03_verify.sql`を実行します。旧8ポリシーの不在、匿名の実効書込権限ゼロ、旧公式戦ポリシー不在、共有RPC、新trigger、既存業務行ハッシュ不変を確認します。匿名のイベント・子データ直接参照はゼロ、有効な共有トークンは表示可、無効/停止/削除時は表示不可と確認します。トークンや内部IDを公開ログへ出力しません。
7. ステージングで再現した実ユーザーの正常系・拒否系を再確認し、Security Advisorを実行します。問題がなければ書き込みを再開します。バックアップ後の正規操作もハッシュ差分になるため、行比較は必ず操作再開前に行います。
8. 問題時は再び書き込みを止め、旧アプリへの復帰と`04_rollback.sql`を同じ作業内で実施します。まず末尾`ROLLBACK`で予行し、結果を確認した復旧担当者が実復旧用だけを`COMMIT`へ変更します。古いバックアップを後日の別変更へ適用しません。切り戻しで旧RLSのP0リスクが再発するため、必要に応じ公開を停止した状態で復旧します。

切り戻しは取得済みの9表ポリシー、public通常テーブルのPUBLIC/anon/authenticatedへのテーブル/列GRANTとRLS状態を復元し、新しいP0トリガー・RPC・内部関数を取り除きます。`CASCADE`は使わず、想定外の依存や列定義変更があれば中止します。既に実施済みの匿名書込撤回と公式戦の無条件ポリシー削除は維持します。0039の監査・バックアップ・同意・統合履歴や、既存選手/試合行は復元対象にしません。

## PR #159のレビュー指摘への対応

今回の追加コミットは戦績ID整合性とチームサイド所属変更の2点だけを対象にします。実データの照会・変更や認証は行わず、リポジトリのDDL・画面・架空データで調査しています。

### 戦績の2種類のID

`app/events/[id]/page.tsx`の`profileMap`は参加者の`profile_id ?? player_profile_id`を使用します。旧アカウントIDと独立した選手プロフィールIDの両方が渡る設計なので、この優先順位は変更しません。旧版の`valid_stats_profile`は`club_members.profile_id`と`player_profiles.linked_auth_user_id`だけを比較し、選手IDの直接一致と有効な所属の確認が不足していました。

修正後は呼出者のグループ権限に加え、対象の`club_members.is_active`、選手プロフィールがある場合の`player_profiles.is_active`を確認し、旧アカウントID・所属の選手ID・連携アカウントIDを同じ所属行から照合します。INSERTだけでなくUPDATEも検証し、無効化後の戦績書き換えを拒否します。

同じ人物のアカウントID行と選手ID行が既に併存していても、自動統合や別形式への書き換えは行いません。現在の参加者に指定されたID形式で保存し、既存の累計は保持します。

さらに0001由来の`player_stats.profile_id → profiles.id`のFKは、独立した選手IDを拒否します。新規IDを保存するために偽のアカウント行は作成しません。P0 SQLでは既知のアカウント用FKだけを外し、上記のRLS/triggerで両ID形式を検証します。未知のFK構成では適用を中止します。旧FKのアカウント削除時の連動削除は専用の非公開triggerで維持し、選手プロフィールが物理削除された場合も同じIDの戦績を削除します。これは将来の親削除時の整合性保護であり、SQL適用時に既存行を削除・更新する処理ではありません。

バックアップ・切り戻しSQLも旧FKを記録・復元します。**新しい選手ID形式の戦績を保存した後は、旧アカウント専用FKへそのまま戻せない場合があります。** その場合はデータを削除せず復旧を中止します。本番適用前に、この状態でのアプリ復旧／DB復旧の方針をステージングで確定する必要があります。旧版の権限バックアップしかない場合も自動復旧しません。

`club_id IS NULL`の旧戦績は適用・再適用でも全列を保持します。一般ユーザーにはグループを特定できない累計行を返さず、スーパー管理者のみ参照でき、書き込みは拒否します。イベント画面の戦績更新は明示したグループだけを扱います。プロフィール戦績は試合結果から算出するため、この旧累計行を表示の根拠にしていません。NULL行の所属先を推測した移管や再集計は行わず、今後、試合履歴・バックアップとの照合結果を別途レビューして対応を決定します。

未連携選手IDの新しい累計が存在する場合、0039の既存ガードが本人統合を安全側で中止することをローカルで確認しました。0039の統合・監査処理は今回変更しません。戦績のない既存の本人承認・統合は回帰テストを通過していますが、**新形式の累計を持つ未連携選手の本人統合は、別途データ処理方針を決めるまで完了できません。** この組み合わせを本番適用前の確認事項とし、戦績を自動移管して回避しません。

### チームサイドの所属変更

既存画面にはグループの変更／グループなしへの変更があるため、`club_id`を全面的な変更禁止項目にはしません。変更後の行を新しい非公開helperで照合し、RLSのWITH CHECKと親子検証triggerの両方から検査します。

- グループを変えずに名称を編集する操作は、従来どおりイベント作成者と双方の正規管理者に許可します。
- `club_id`を変える場合は、開催中イベントの運営権限に加え、変更元・変更先の非NULLグループそれぞれでメイン／サブ管理者（またはスーパー管理者）であることが必要です。両方の権限を持つ本人の保存操作を承認とし、片側の権限だけでは第三者グループへ移せません。
- グループなし→グループは変更先、グループ→なしは変更元の管理権限が必要です。変更によってイベントの最後の閲覧・運営権限を失った場合、以後そのユーザーは操作できません。
- 新規作成時の相手サイド登録は維持します。サイドの直接DELETEは、削除→INSERTによる所属変更の迂回になるため拒否します。既存画面はサイドのUPDATEを使用し、イベント削除に伴うサイドの連動削除は維持します。
- 異なる管理者による個別の共同承認フローは追加していません。両グループの管理権限を持つユーザー／スーパー管理者による操作ができない場合は変更を拒否し、将来の承認設計を別途検討します。

画面はDBで所属変更が拒否された場合に日本語のエラーを表示します。作成、相手サイド登録、双方の通常編集、許可された所属変更、第三者グループへの変更拒否をローカルSQLで確認しています。

## 影響と依存機能

DB側の拒否が新たに有効になるため、旧データの親子不整合やクライアントの所属指定漏れはエラーとして現れます。戦績の読み書きはクラブを明示するよう合わせ、個人イベントのクラブなし戦績は作成しません。既存のクラブなし戦績は削除せず、移管・再集計は別途レビューします。試合/イベントそのものの記録と、試合結果から算出するプロフィール戦績は維持します。終了済みイベントの読込時は新しい会員を自動追加しません。所属旧状態の不一致、クラブなし旧累計、既存の累計二重加算などのデータ補正は実施していません。

依存する機能はグループ検索/作成、本人プロフィール連携0039、参加者自動反映、通常/手動/チームのイベント、Round/結果/ランキング、終了/再開、公開共有/動画リンク/クリック、スーパー管理者の件数表示です。ゲストモードの保存はsessionStorageで完結し、DBへの匿名書込に依存しません。Round生成アルゴリズム、利用規約、Cloudflareの実行方式は変更しません。
