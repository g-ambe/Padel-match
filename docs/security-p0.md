# PR #159：P0権限保護と既存機能の互換性

既存ブランチと同じDraft PRで対応します。本番へのSQL送信・設定変更・データ変更、mainへのマージは行っていません。Googleログイン、Round生成アルゴリズム、公平性、休憩ローテーション、ゲーム形式、スーパー管理者の正式登録は変更しません。

## 保存と権限

- 在籍の判定は既存UIの退会・復帰操作と同じis_activeへ統一します。旧status列や所属行は書き換えません。
- 8テーブルの無条件ポリシーを所属・役職・状態のRLSへ置換し、親子IDの付け替えとグループ／イベントの直接DELETEを拒否します。通常メンバーのイベント運営と既存UIの役割制限は維持します。
- スコア、Roundと全試合・参加枠、未採点の組合せ、試合削除、終了・再開・論理削除、グループと初回管理者、チームイベントと両サイドをトランザクションRPCで保存します。要求UUID・内容・本人を照合し、再送を冪等にします。
- 試合結果が正本です。結果・完了状態・影響する選手の累計を同じトランザクションで処理します。再編集・引き分け・削除・反映対象変更も対象選手だけを算出します。player_statsの直接INSERT/UPDATE/DELETEは管理者を含むAPIロールから撤回します。
- 既存累計と正本が一致しない場合や複数のID形式が曖昧に重なる場合は、自動補正せず操作全体を中止します。対象件数・補正理由・復旧計画を提示して承認を得るまで既存数値を保持します。
- 匿名共有は有効なトークンを検証する表示専用RPCを使い、内部の認証・プロフィールIDやトークン自体を返しません。

## 本人承認と戦績

アカウントと選手プロフィールは別テーブルのままです。未連携の仮選手でも参加・戦績保存でき、本人がメール確認・メール／パスワードでログインして正規プロフィールを作成した後、0039の管理者申請＋本人承認、または本人の加入同意＋管理者承認を使います。

0039の本人照合、失効、役職保護、同じイベント／試合での重複検査は維持します。統合時は所属・参加者・チーム戦・公式戦・累計を引き継ぎます。match_playersは参加者IDを維持し、試合・出場枠・結果を作り直しません。本人の表示名や設定も仮選手の内容で上書きしません。

累計の移動・合算は本人承認のトランザクション内だけで行い、削除する元累計も含めた変更前後を0039の監査へ保存します。確認トークンには源泉の戦績と統合先の累計状態を含め、確認後の変更を拒否します。画面にも引き継ぐ累計件数を表示します。

旧版の加入同意に累計項目がなくても、新しい累計がなく他の情報が不変なら承認できます。未同意の累計があれば再同意が必要です。保存済み同意の自動書換えは行いません。同じグループの二重所属、同じ試合の二重枠、曖昧な累計の重なりは、権限や数値を推測して統合せず確認待ちにします。

## チームの許可条件

作成画面のグループ選択肢は従来から管理グループです。INSERTにもメイン／サブ管理者の同条件を適用し、第三者グループを指定した権限付与を拒否します。管理するグループ同士の選択、登録後の双方の管理者による通常編集は維持します。管理しない正当な相手は、従来どおり自由入力のチーム名・ゲストで登録できます。

所属変更には変更元・変更先の各非NULLグループの管理権限が必要です。グループなしへの変更は変更元、なしからの変更は変更先を検証します。削除→再INSERTやサイド識別子変更による迂回を拒否します。共同承認の新機能は追加していません。

## データ保護・適用手順

マイグレーション適用時の既存業務行の更新・移管・削除・再集計は **0件** です。実環境の行数は未照会で、補正対象の実件数は不明です。club_id IS NULLの旧累計は保持し、所属先を推測しません。一般ユーザーには非表示、スーパー管理者だけ参照できます。プロフィール戦績は試合結果から算出し、この旧累計を表示の根拠にしません。

NULL旧累計の今後の対応は、選手と正本試合から所属先を特定できるもの・できないものを読み取りで分類し、件数・表示方針・変更理由・復旧方法を提示して別途承認を得ます。所属先が曖昧な行は保持します。今回の適用で移管や再集計を行う計画はありません。

独立した選手IDを拒否する旧アカウント専用FKは、所属検証と削除トリガーへ置換します。将来、親IDが実際に物理削除された場合の後処理を定義するだけで、適用時に削除は実行しません。未知のFK構成では適用を中止します。

1. [01_preflight.sql](../supabase/maintenance/security-p0/01_preflight.sql)で実スキーマ、重複結果、空Round、勝敗不一致、累計差分・ID重複、NULL行を読み取り確認します。補正候補の算出だけで保存値は変更しません。
2. 差分がある場合は対象件数・理由・復旧方法を提示し、承認待ちにします。今回、実データの補正は実行していません。
3. [ステージング手順](security-p0-compatibility.md)の実JWT・PostgREST・ブラウザ試験を完了します。未実施をPASSにしません。
4. PRレビューと適用承認後、DB全体のバックアップ／PITRを確保します。統合監査、profile_link_private、security_p0_historyも含め復元可能性を確認します。新しい履歴スキーマをData APIへ公開しません。
5. 書き込み停止後に[02_backup.sql](../supabase/maintenance/security-p0/02_backup.sql)を取得し、今回のP0 SQLだけを手動適用します。過去migrationの一括db pushは行いません。
6. RPCを使うアプリとSQLをメンテナンス中に揃えます。旧クライアントの直接累計更新は拒否されるため、公開中に切替間隙を作りません。
7. 操作再開前に[03_verify.sql](../supabase/maintenance/security-p0/03_verify.sql)で業務行の件数・ハッシュ不変、権限・RPC・トリガーを確認します。Advisorもステージングで確認し、本番は別途承認した運用で扱います。

## 障害対応・切り戻し

稼働後は互換DBと監査を保持する前進修正を優先し、旧形式への強制変換はしません。

- 非公開のsecurity_p0_history.operationsへ、本人・要求・結果・変更前後を同時記録します。バックアップにも含め、秘密情報を結果ログやPRへ出力しません。
- [05_inspect_operation.sql](../supabase/maintenance/security-p0/05_inspect_operation.sql)で対象ID・件数・理由を提示して承認を得ます。[06_restore_operation.sql](../supabase/maintenance/security-p0/06_restore_operation.sql)は確認済み件数を明示して既定ROLLBACKで予行します。操作後の変更や新しい子履歴があれば、上書き・連動削除せず中止します。
- [本人統合の復旧](../supabase/maintenance/profile-linking/04_restore_reviewed_merge.sql)は、監査済みの移動・合算・削除行を戻せます。統合後の編集があれば停止し、監査・同意の履歴は削除しません。
- [04_rollback.sql](../supabase/maintenance/security-p0/04_rollback.sql)によるDB権限の全体切り戻しは、稼働後の操作がまだない段階だけが対象です。未復旧の操作や旧FKへ戻せない選手ID累計があれば停止します。新しい操作監査は保持します。旧RLSのP0問題が再発するため、公開停止のまま復旧を判断します。

実施者、ref、Git SHA、SQLチェックサム、対象件数、承認者、バックアップ識別子を安全な適用台帳へ記録します。今回は手順作成と架空データの復旧試験までで、本番の障害対応は実行していません。
