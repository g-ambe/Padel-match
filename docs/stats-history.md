# 戦績の集計元とイベント削除（2026年10月29日）

## 調査結果

基準は改修前の main `8f4e1bf`。アプリ・ライブラリ・コンポーネントと、リポジトリ内のマイグレーションを確認した。本番Supabaseには接続していない。

| 箇所 | 従来の集計元・条件 | 今回の対応 |
| --- | --- | --- |
| プロフィール総合戦績 | 本人に紐づく選手IDと旧 `profile_id` のメンバー参加履歴 → `match_players` → `matches` / `match_results` | 正式戦績対象イベントの取得を共通化。計算と試合IDによる重複除外は維持 |
| グループ個人・ペアランキング | 終了済み・未削除・`official` のイベント、全4人が所属履歴からメンバーと判定される試合 | 同じ対象判定のまま、イベント・所属・参加者・選手名・試合をページング。取得失敗時は古いランキングを消してエラーを表示 |
| 通常イベント内の進行中ランキング・終了サマリー | そのイベントの試合・参加者・スコア | 計算・表示・ゲストモードは変更なし。削除済みイベントは既存の削除済み表示へ |
| フレンドリーチーム戦 | `event_team_matches` を用いるイベント内の独立集計 | 計算・対象条件・順序は変更なし。削除拒否・0行更新を検出。再取得時に削除済み・取得不能なら古い詳細戦績を消す |
| オフィシャル戦 | `official_matches` を用い `buildOfficialStats` で相手別・選手別・ペア別に集計 | 計算・対象条件・順序は変更なし。削除時の更新件数検証、再取得失敗時の詳細戦績クリア |
| 公開共有画面 | 未削除・終了済み・共有有効のイベントの試合履歴 | 条件・計算は変更なし。記録用イベントを共有して結果を見る既存仕様も維持 |
| 通常のイベント履歴一覧 | home・グループ・チーム戦・公式戦一覧で削除済みを除外 | 除外条件は維持。super_userの管理用一覧で削除済みを確認する既存仕様も維持 |
| `player_stats` | 通常イベントのスコア保存時に加算、試合削除時に減算。画面表示への参照はなし | 加減算とそのための読取りを停止。テーブル・保存済み値・制約・権限は保持 |

スコアを編集して再保存しても旧累計に再加算する実装だった。イベント終了・再開・論理削除と累計値を同期する処理はなく、累計は履歴と食い違う可能性があった。画面は既に履歴を利用しているため、画面の参照元を旧累計へ切り替える作業は不要だった。

アプリの `app` / `lib` / `components` から `player_stats` へのアクセスはなくなった。既存の `0039_player_profile_consent_linking.sql` は旧 `profile_id` の整合性を守るために同テーブルの存在を確認する。この安全確認は戦績の計算ではないので変更していない。既存の修復SQL・プロフィール統合SQL・DBテストも保持する。リポジトリのマイグレーションに、スコアから `player_stats` を自動更新するトリガーはなかった。本番固有の追加処理や外部クライアントは未確認。

## 維持した計算式と対象条件

通常の正式戦績は `status = 'closed' AND is_deleted = false AND stats_mode = 'official'`。試合は既存の `hasEnteredFriendlyMatchScore` により `completed = true` と有限の数値スコア両方を必要とする。有効な0対0の引き分けも数える。未終了・再開中・削除済み・記録用・未確定を正式戦績へ追加しない。

- 個人：試合IDで1回だけ計上。勝利は従来どおり `winner_team` と本人のチームを比較。勝率は勝数÷試合数×100、平均得点・失点はそれぞれ合計÷試合数。ゲストの同席を理由に除外せず、複数グループ分も集計する。
- グループ：所属行は退会済みを含めて全件使用。全4人・各チーム2人がその所属履歴に結びつく試合のみ計上。勝敗・引き分けはスコア比較。個人・ペアとも勝点は勝数×3＋引き分け数。
- 総合ポイント：勝率×0.7＋（試合数÷最大試合数×100）×0.2＋（max(0,得失点差)÷最大の正の得失点差×100）×0.1。両分母は最低1。正規化は退会者を含む元の集計結果で行い、表示時だけ現在在籍する選手・両名が在籍するペアに絞る。3試合未満は参考記録。
- 個人の総合順：総合ポイント→勝点→勝率→勝数→引き分け数→得失点差の降順、試合数の昇順。勝率順：勝率→勝数→引き分け数→得失点差→得点→試合数の降順。明示的な同点条件は変更していない。
- ペア順：勝点→勝数→勝率→得失点差→得点→引き分け数の降順、試合数の昇順、ペア名の日本語順。平均得失点差・表示項目も維持。
- フレンドリーチーム戦：別テーブル・別の計算のまま。既存の「両スコアが数値、0対0は除外」、得点比較による勝敗、勝点・丸め・並び順を維持。記録用を含めたイベント内の結果表示を通常の正式個人・グループ戦績へ合算しない。
- オフィシャル戦：`undecided` 以外の結果を計上し、勝数降順→勝率降順→名称日本語順。ゲストを含む相手別・選手別・ペア別の分類と勝率の小数1桁への丸めを維持。

グループの計算部分（`const pStats` 以降）と画面上の順位付け、プロフィールの数値集計部分は同じコードを残した。改修前コードを固定した `tests/fixtures/legacy-stats.ts.txt` と実際の画面関数を比較し、30パターンの履歴で各項目・配列順序まで一致を検証する。共有関数に移したのは取得・対象イベント条件であり、個人とグループの計算を統一したわけではない。

## 削除・修正後の再集計

イベント削除は既存の論理削除（`is_deleted` と `deleted_at` の更新）を維持し、該当する履歴を取得対象から外す。通常・チーム・公式それぞれの画面で、更新が1行だったことを `count: 'exact'` で確認する。削除後の行を返却させないため、削除済み行がSELECTで隠れるRLSとも両立する。エラー・0行更新では成功遷移しない。

イベント・参加者・Round・試合・スコア・動画URL・選手プロフィール・所属・アカウント連携を物理削除する処理は追加しない。チーム・公式の既存の共有停止もそのまま。試合単体の削除機能は従来どおり対象試合だけを削除し、旧累計値の減算は行わない。保存済み累計値を期待値にはしない。

次に画面を読み込むと、有効なイベントと最新の試合履歴から各画面固有の式で再計算する。スコア修正は更新後の値、試合削除は残った試合だけが対象。イベント終了・再開は対象条件が切り替わる。累計の再構築SQLや手動の加減算は不要。イベントを将来復元する場合にも、保持した履歴から再現できる（復元操作は今回追加しない）。

## 未検証・残存する制約

- ステージングの接続先は確認できず、ステージング・本番の実アカウント・実際の適用済みRLS・本番固有のトリガーは未検証。本番データの件数や旧累計との実差分も取得していない。
- `0036` のチーム戦用UPDATEポリシー単独では `is_deleted = false` を更新後にも要求する。他の適用済みポリシーや管理者の所属次第で論理削除が拒否される可能性がある。今回は指定どおりRLSを変更せず、拒否された場合に成功と表示しない。実環境では作成者・両チームの管理者・super_userで削除可否を確認すること。
- 複数のHTTPリクエストを使う既存のスコア保存（結果と確定）・試合単体削除・ページング全体のDBトランザクション化は行っていない。途中失敗はエラーとし、スコアは再保存できる。複数端末の同時編集や、ページ取得中の他端末からの変更まで単一スナップショットで保証するには別設計が必要。
- リアルタイムの自動再読込みは追加していない。他端末からの削除・修正は画面を再読込みして確認する。
- グループ履歴は全件取得するため、大規模な履歴ではHTTPリクエスト数・応答時間が増える。500行ページングは現行の通常のSupabase取得上限（1,000行）を想定し、それより小さい独自上限は未検証。
- 既存の画面に表示する戦績・計算ルールを維持しており、新しい集計区分、復元UI、DB制約変更、古い累計値の修復は追加しない。
