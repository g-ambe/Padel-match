# 在籍状態と既存権限の確認

アプリは所属の `is_active` だけを更新します。選手・アカウント・連携・役職・履歴は削除/更新しません。今回のSQLは自動適用しません。新しいマイグレーションやテーブル・列の追加もありません。

従来の0039等には、所属判定で旧状態列を併用するDB関数・公式イベントのRLSがあります。その定義が残る環境では、退会済み行の `is_active` をtrueに戻しても管理権限や公式イベント閲覧が戻らず、復帰した仮選手の連携申請もできない可能性があります。ブラウザの更新列を変えるだけではDB内の条件を直せないため、既存の役職・本人承認条件を維持して所属判定だけを統一するSQL案を用意しています。

1. Supabaseのバックアップを確認し、管理者のSQL Editorで `01_check_access.sql` を実行します。出力された変更前の関数定義・ACL、ポリシー、既存トリガーをDB外へ保存してください。RESTでの列確認だけでRLSの実態は断定できません。
2. 旧所属判定が確認された場合、`02_use_is_active.sql` をステージングで末尾ROLLBACKのまま試し、確認後に末尾だけCOMMITへ変更して手動適用します。未確認のポリシーが残ったら中止し、広いUPDATE許可は追加しません。既存の申請承認・統合・通知の仕様や実行権限を変えず、所属判定だけを修正します。
3. 最後のメイン管理者はアプリでも再取得して確認します。複数管理者が別々の行を同時に退会・降格する操作までDB側で防ぐには `03_guard_last_admin.sql` が必要です。ステージングでROLLBACK試行後、確認して手動COMMITしてください。グループ行のロックで同時操作を直列化し、所属以外のデータは更新しません。
4. 退会・復帰後の役職、通常/公式イベントの閲覧・参加候補、既存の連携承認・統合、super_user、42501/42703/42P17がないことを確認します。本番への自動適用・デプロイは行っていません。

02はCREATE OR REPLACEと既存ポリシーのALTERのみです。適用前の定義と比較し、独自変更がある場合は先にレビューしてください。既存マイグレーションは書き換えません。途中エラーはROLLBACKします。適用後に戻す必要がある場合は編集を停止し、保存した変更前定義・ACLで個別復旧します。03だけを戻す場合は管理者が対象トリガーと関数だけを確認して削除でき、所属・プロフィール・履歴を戻す必要はありません。
