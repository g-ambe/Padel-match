# PR #182：重複結果の調査・修復承認

**2026-11-06に、91試合・213行・余剰122行と固定プランSHA、承認済み5 SQLの原子的適用についてユーザーが明示承認済み。** `approval-plan.json` の範囲を拡張しない。ユーザーによるSQL操作は不要で、Codexの管理用クラウド実行から進める。本番適用は最新の外部バックアップ・独立した隔離復元・修復/復旧・全検査の成功後だけ行う。

## 調査範囲と原因

`01_audit.sql` は読み取り専用。全形式の重複、日付・時間差・行数の分布、参照外部キー・ビュー・関数・索引を調べ、氏名・試合ID・結果ID・実スコアを返さない。`plan.sql` の実データは暗号化保管専用でログ禁止。対象全行・開催情報を含むJSONBのSHA-256で、読み取り調査と承認対象を照合する。

過去の保存実装（例：`96dac31`、`08b89ac`）は、画面に結果IDがなければINSERTし、通信中の連打防止・結果の再確認・DBの試合ID一意制約がなかった。画面更新前の再保存、別端末の同時保存、INSERT応答喪失後の再送で重複を作れる。再現試験は実PostgreSQLの複数接続で確認する。実データの作成時刻は5月15日〜10月23日（UTC）、全重複が1分以内、59試合が1秒以内。10月29日以降の自動保存UI導入より前から存在する。端末・操作ログがないため、各行が連打・複数端末・再送のどれによるかは断定しない。

現行mainの保存キューは同一画面内の二重送信を抑え、既存行の取得エラーをINSERTへ流さない。しかしSELECT→INSERTは複数端末に対して原子的ではなく、現行DBにもPK(id)以外の一意索引がない。旧端末の結果IDキャッシュは修復後に古くなる可能性があるため、実施後は再読み込みする。新しい一意制約は二重行を防止するもので、従来の未入替イベントにおける旧クライアント同士のUPDATEを全面的にCAS化する変更ではない。入替済みRoundの旧保存は0041/42で拒否し、新画面は構成・結果の期待値と要求IDを検証する。PR #182のRPCは通常乱数イベントの期待値・要求ID・イベントロックを検証する。0043の `UNIQUE(match_id)` は手動イベントや旧クライアントも含めDBで重複を拒否する。

## 提案対象と正本

初回の89試合・余剰120行は通常乱数イベントだけの集計。全形式では、削除済み手動イベント2試合・余剰2行が加わり、**91試合・213行から122行を整理し、91行を保持**する。全試合で得点・勝敗が完全一致。終了済みの正式記録87試合、削除済みの乱数2試合、削除済みの手動2試合。開催中は0件。追加の2試合も承認範囲に含め、89試合だけの承認で自動拡張しない。

正本は同一match_id内で `created_at ASC NULLS LAST, id ASC` の先頭。最初の記録ID・作成日時をできるだけ残し、日時が同じ場合もUUID順で再現可能にする。得点が一致することと参照の安全性が前提であり、最古の値を無条件に正しいとみなす方式ではない。現対象にNULL日時はなく、同一日時の重複もUUIDで一意に決める。

スコアが食い違う、対象行・開催状態が変わる、新しい重複が増える、参照が見つかる場合は停止する。ユーザーが承認した非公開プラン以外を自動選択しない。

## 参照・戦績への影響

外部キーによる結果ID参照は検出0件。さらに候補122 IDについて、publicの他の全実テーブルのUUID・JSON・文字列参照も検査し、該当があれば停止する。バックアップ用の別スキーマは変更しない。参照ガードやプロフィール統合関数がmatch_resultsを読み取ることと、特定の結果IDを保持して参照することを区別する。

現行のグループ・個人・開催・共有・バランスペアの集計は、同じ試合の結果配列先頭を1件使う。修復候補はすべて同値なので、結果行の物理件数は減るが、試合ごとの得点・勝敗は変えない。実バックアップで、アプリの既存関数そのものを使い、13グループ・84プロフィール・81イベントの戦績、ランキング、MVPを修復前後・復旧後でハッシュ比較する。チーム戦・公式戦の記録は別テーブルで、全行不変を確認する。旧 `player_stats` の累計は現行UIの正本ではなく、今回書き換えない。

## 原子的な修復と監査

`02_repair_reviewed.sql` は入力がなければ例外で全体停止する。承認済みプラン、SHA、バッチUUIDを実行器が安全に注入する。本文を部分実行しない。

- 同一試合の全結果が一致すること、削除IDへのFK・public内参照がないことを再確認する。
- 承認プランと実データの全行JSON・match・eventが完全一致しなければ中止する。
- publicの参照候補テーブルをロックし、確認後に参照が追加されることを防ぐ。待機5秒・実行60秒で、実施時間帯を確保する。
- `score_repair_182.batches/rows` に保持行を含む全213行、対応する正本ID、元JSON、計画SHA、修復前後ハッシュ、実行者、日時、削除件数を保存する。一般利用者・匿名・service_roleへ権限を与えない。
- 承認された非正本だけをDELETEし、件数・正本の完全一致・試合ごとの結果一致を検証する。途中の失敗は監査DDL・削除ともROLLBACKする。
- 同じバッチの二重実行は、修復後状態が完全一致する場合だけ無変更で終了する。変更後の状態へ古い要求を適用しない。

**本番では修復と0041→0042→0043の全SQL文を同じトランザクションで適用する。** BEGIN/COMMITだけを外側へまとめ、一意制約を作る前に旧クライアントのINSERTが入り込む隙間を作らない。0043の失敗でも修復と0041/42をすべてROLLBACKする。RLS・GRANT・既存保護トリガーを解除して進めない。

0043はmatch_resultsだけの `UNIQUE(match_id)`。通常・手動とも1試合に1組の得点であり、正当な複数セット記録の形式は存在しない。フレンドリーチーム戦・公式戦は別テーブル。既存のnullable仕様を変えず、NULL match_idの複数行を追加で禁止する変更はしない（現データは0件）。

## 復旧

`03_recover_reviewed.sql` は既定ROLLBACK。承認したバッチと全計画のSHAを照合し、修復後の全結果ハッシュ・カラム構造が変わっていたら一括復旧を拒否する。更新済みの正本を上書きしない。

原状復旧では、0043で追加した一意制約だけを、定義が完全一致する場合に戻してから、監査の元JSONから全ID・得点・勝敗・作成日時を復元する。元の重複を戻すための限定的な手順であり、通常運用の再発防止を解除する手段にはしない。既存のRLS・FK・トリガーは解除せず、CASCADEも使わない。0041があれば入替停止を必須とする。

復旧後に元の全結果ハッシュへ一致すること、再実行が無変更で終わることを隔離DBで検証する。監査・元のDB外バックアップは残す。修復後に実データが更新された場合は、この一括復旧を強行せず、監査に基づく別の個別復旧を設計する。旧Workerへの切り戻しだけでDB状態が戻るとは扱わない。

## 承認後の順序

1. 非公開の計画・保持規則・91試合/122行の範囲・0043・復旧の条件について明示承認を取得する。
2. 最新の読み取り調査で計画SHA、参照、カタログを再確認する。一致しなければ対象を変更せず停止する。
3. 修復前の新しいDB外バックアップを暗号化・別保管し、保管した実ファイルを隔離復元して照合する。既存のFreeプラン自動バックアップを前提にしない。
4. 停止時間帯に、承認済み修復と0041/42/43を原子的に適用する。適用後は `04_verify.sql` と既存のRPC・権限検証、戦績比較を実行する。入替はまだ無効。
5. 最新PRの全チェック成功を確認してSquash mergeし、既存のCloudflare自動反映を確認する。
6. 専用テストイベントでスコア・修正・生成・終了を検証してから入替を有効化する。既存試合で破壊的試験をしない。

承認前は既存の本番Migration実行器にも明示承認のガードを設ける。`approval-plan.json` が承認済みでない、または承認したSQLのSHAが変わっていれば、本番への準備・適用を開始しない。現在のリハーサル・読み取り調査の結果と承認対象のSHAは、PR #182の説明に記録する。非公開の個別計画をGitやログに載せない。本番修復アクションは承認前には追加・実行しない。
