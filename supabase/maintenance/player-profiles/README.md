# プロフィール重複の調査・手動修復手順

0039以降の本人承認による連携は [新しい連携・統合手順](../profile-linking/README.md) を使用します。このディレクトリは過去の重複調査・修復記録として保持し、設定済み53行を再実行しません。新仕様では有効な正規プロフィールをアカウントごとに1件以下とし、既存の複数連携は本人確認まで移行を停止します。

このディレクトリは通常のマイグレーションではありません。アプリ・ビルド・CIからSQLを実行しません。実DBへの統合、連携解除、無効化、削除は今回のコード修正で実行していません。

## 原因と設計の確認

- `app/profile/page.tsx` は `linked_auth_user_id` の取得に `maybeSingle()` を使用し、エラーを確認せず `data` がなければ INSERT していました。2件以上存在すると取得が失敗し、画面の再表示が次の重複を作る経路になります。通信失敗・RLS・列不足なども同じ分岐に入ります。
- 新規登録と加入申請の承認にも同様の分岐がありました。グループ作成も取得エラーを無視して新規選手を作成していました。
- 保存では UPDATE のエラーしか見ておらず、RLSや連携変更によって更新0件でも成功表示し、入力値をそのまま画面に反映していました。
- `0007_player_profiles.sql` は認証ユーザーと選手を分離しています。グループのメンバー追加は別の選手を作成でき、アカウント連携の重複チェックも同じグループ内だけです。別グループの選手を同じアカウントへ連携できる既存仕様を維持し、`linked_auth_user_id` の全体 UNIQUE 制約は追加していません。
- ログイン・グループ閲覧・権限判定には、連携する全選手のIDを使う実装もあります。重複を無条件に削除すると所属・参加者・権限・履歴を失う可能性があります。特に `club_members.player_profile_id` のFKは削除カスケードです。

## 読み取り専用で確認した状況

2026-10-22に接続済み設定を使い、REST経由の読み取りだけを行いました。確認時点で全78件、連携済み62件、7アカウント、アカウント別件数は54 / 2 / 2 / 1 / 1 / 1 / 1、詳細入力済み2件でした。

54件のアカウントでは、次の情報が異なる選手IDに分散していました。

| 候補 | 詳細設定 | 所属行 | 参加履歴 | 公式戦の参照 |
| --- | ---: | ---: | ---: | ---: |
| 履歴の主候補 | 0項目 | 3件 | 50件 | 3試合 |
| 別グループの履歴候補 | 0項目 | 1件 | 2件 | 0試合 |
| 保存済み設定の候補 | 3項目 | 0件 | 0件 | 0試合 |

残る51件は、今回読み取れた範囲では詳細設定と関連参照がありませんでした。4件の所属は別々のグループで、同じイベント内の複数選手も読み取り範囲では見つかりませんでした。最新レコードだけを残す方法は採用できません。

RESTで取得したプロフィール設定・履歴のコピーはチェックアウト外の作業用領域に保管しています。今回提示された修復対象UUIDだけを03の確認用プランに収録しています。RESTの読み取りはRLSで見える行に限られ、同時点のトランザクションでもありません。**完全バックアップや「参照なし」の確定根拠にはせず、管理者による以下のSQL確認を優先してください。**

## 今回の53行の確認用プラン

[03_repair_reviewed_plan.sql](03_repair_reviewed_plan.sql) に提示された対応表を設定済みです。末尾はROLLBACKで、本人・管理者の保持先承認や実DBへの適用を済ませたという意味ではありません。

| 対象 | 移行元行数 | 保持先ID | 保持先の設定 | 所属行 / 参加履歴 |
| --- | ---: | --- | --- | ---: |
| ごーき | 51 | `ebb5ce50-a6f7-45ec-b7fa-92a49f3aab2c` | 入力あり | 0 / 0 |
| 瀧田 | 1 | `2a843167-2875-4c8b-b2b2-98860a2f2517` | 空欄 | 1 / 38 |
| 上田 | 1 | `acce99ab-1bd7-47c3-bb8b-8c80e7d22466` | 空欄 | 1 / 6 |

上表は2026-10-23のREST再確認時点で見えた範囲です。53行すべてで元・先の連携アカウントが一致し、保持先は有効な別々の3アカウントで、詳細5項目の衝突は見つかりませんでした。移行元53行には、読み取れた範囲で詳細入力と既知の関連参照はありませんでした。瀧田・上田の保持先は暫定案のままなので、全所属・戦績と本人・管理者の判断を確認してください。

安倍 `3f787ec6-d6f4-48ee-934d-7f00bacda625` とテスト01 `71d12eaf-fcd3-4df2-a7d4-5319498f9643` は移行元・移行先の両方から除外します。2行合計で所属4行・参加52行・公式戦3試合の参照が見えています。これらのプロフィールと履歴はそのまま保持し、連携解除・無効化しません。ごーきには保持先と除外2行が残るため、プロフィール画面では引き続き選手の選択が必要な場合があります。

確認時の全プロフィール数は79件で、前回の78件から変化しています。古いバックアップに合わせて比較検査を外さず、メンテナンス中の最新状態を02で保存してください。既存バックアップは上書きせず、別の保存先名を使う場合は02〜05の参照名を揃えます。

03は53行・保持先3名、指定した保持先IDと内訳51・1・1、対象外IDの混入、3アカウントの区別を検査します。内容を変更する場合は、対応表・検査条件・テストを再レビューしてください。保持先を単純に最新レコードへ変更せず、所属・参加・戦績と保存済み設定を優先して確認します。

## コード修正後の動作

- プロフィール画面の読み込み・再読み込みは SELECT のみです。未登録でも表示だけで INSERT しません。
- 複数件を配列として読み、設定・所属・参加・フレンドリーチーム戦・公式戦・加入申請の参照を確認します。情報を保持する候補が複数ある場合は、最新・最古・参照数だけで決めず、画面で選択します。54件のケースも明示選択が必要です。
- プロフィール選択はアカウント別にブラウザへ保存し、同じブラウザでのログアウト・再ログインでも同じIDを利用します。別ブラウザでは再選択が必要です。これはDBの統合や全端末共通の代表ID登録ではありません。
- 所属とプロフィールの総合戦績は連携中の全選手を対象に読みます。同じ試合IDは二重計上しません。グループ内の個人・ペア戦績、既存イベントや試合の参照先は変更していません。
- 関連情報の取得失敗は警告し、未確認の所属を「未所属」や戦績を0件と断定しません。選択済みのプロフィール自体は読める場合に表示します。
- 未登録時の作成は明示操作に限定します。アカウント作成・グループ作成・加入承認で必要になる初期選手のIDは認証ユーザーIDに固定し、同時作成・再試行を既存主キーで抑止します。既存選手のIDは変更せず、取得エラーや候補の曖昧さがあれば新規作成しません。
- メール確認が必要な新規登録では、未認証の `user` 情報からプロフィールを作成しません。認証後の初回メールログイン等で認証側の `profiles` を準備する場合も、既存行は上書きしません。
- 保存は選手ID・連携アカウント・編集前の設定値を条件にし、更新1件と再取得した内容の一致を確認します。別の画面からの変更や更新0件、再取得エラーで成功を表示しません。
- グループ管理での既存選手の連携変更・解除も、変更前の連携先と更新1件を確認します。権限関数やsuper_userの定義は変更していません。

## 実DBでの実行順序

SQL Editorの管理者権限で実行します。事前にSupabaseのバックアップ/エクスポートを取得し、復旧先を確認してください。`02_backup.sql` の保存先もDB内なので、DB障害に備える外部バックアップの代わりにはなりません。

1. アプリの修正版を先に適用して増殖経路を止めます。今回の作業ではデプロイしていません。
2. [01_inspect.sql](01_inspect.sql) を実行し、各選手の全設定・所属・参加・戦績・申請、実DBの全FK・索引・トリガーを確認します。FKのない参照列も確認します。権限不足や表不足を「参照なし」と解釈しないでください。
3. メンテナンス中は対象データの編集を止め、[02_backup.sql](02_backup.sql) を実行します。実FKの参照表に加え、公式戦の参照、旧 `profiles`、試合・結果・権限等を同一トランザクションで専用スキーマへ保存します。既存バックアップを上書きせず、anon/authenticatedには公開しません。出力件数を確認・エクスポートしてください。
4. 本人・管理者が「元ID → 保持先ID」を承認します。所属・履歴があるIDを優先して検討し、保存済みの設定は必ず保護します。無関係な別選手、未確認の空行を一括で対応表に入れないでください。
5. [03_repair_reviewed_plan.sql](03_repair_reviewed_plan.sql) の設定済み53行を本人・管理者の承認内容と照合し、**末尾の ROLLBACK を残して**試します。対象・件数・内訳の変更や対象外IDの混入は中止します。バックアップ後のデータ変更、未知のFK、内容衝突、所属・参加者の衝突、同一試合への二重出場も中止します。エラー後はトランザクションをROLLBACKしてください。
6. 出力された before/after を確認します。問題がなければ同じ承認済みプランで末尾だけを手動で COMMIT に変更して実行します。保存先スキーマを変更する場合は02〜05の参照をすべて同じ名前に揃えてください。
7. [04_verify.sql](04_verify.sql) と生成される確認SQLを実行します。全表の件数、移行元への参照残り、孤立した参加者参照、after_rowとの一致を確認します。アプリでも再ログイン後の設定、全グループの所属・役割、イベント参加者、各試合、個人・ペア・グループ戦績、super_userの権限を確認してください。ブラウザに保存した元IDが連携解除された場合は、画面で保持先を選び直します。

03は対象のプロフィール詳細の**空欄だけ**を補完し、所属・参加者・試合・申請の参照列だけを更新します。行IDと全表の行数、グループの役割、試合結果、参加者IDを保持します。移行先の表示名はそのまま残し、元行は表示名・詳細を保持したまま連携解除・無効化します。**DELETEは行いません。** `player_stats.profile_id` や `app_admins.profile_id` は認証側のIDなので付け替えません。

同一グループの複数所属がある場合、役割や在籍状態を機械的に選べません。同一イベントの複数参加者は `match_players.participant_id` の参照もあるため削除・合体せず中止します。これらや未知の参照は、結果を提示して個別の修復計画を作る対象です。

## 元のデータに戻す場合

[05_restore_previous_rows.sql](05_restore_previous_rows.sql) は、03の変更前後の記録を使って変更行だけをUPDATEで戻します。最初は末尾のROLLBACKで試し、確認後に手動COMMITします。修復後に同じ行が編集されていたら中止し、その新しい情報を上書きしません。その場合は新しいバックアップと個別確認が必要です。バックアップスキーマや変更記録は、確認が終わっても自動削除しません。

## 検証

`npm test` は実Supabaseに接続しません。Supabase SDKのHTTP応答を置き換えた回帰テストと、一時PostgreSQL（PGlite）で上記SQLの成功・中止・ロールバック・復旧を検証します。53行の設定済みSQLをそのまま使い、架空の設定・所属・参加・試合を用意して、保持先設定と除外2行の保護、元行を削除しない修復と復旧、誤った対応表の拒否を確認します。Node.js 24で確認しています。

Cloudflare互換性は `npm run cf`（既存 `cf:build` への別名）とTypeScriptで確認します。リポジトリにロックファイルがないため、現行のNext.js 15.3.2でセットアップ済みのOpenNext 1.14.0を利用します。最新版OpenNextに切り替える依存更新はこの修正には含めていません。

実DBは読み取り調査だけです。実アカウントでの保存・認証や修復SQLの適用結果は、モック/一時DBの検証とは区別して手動確認してください。
