# プロフィール表示位置（0049）

既存の非公開R2画像・0048の本人判定、画像変更制限、Instagramの処理を維持する追加Migration。

## 保存と競合

- `player_profile_private` に `avatar_focus_x/y`（0〜1）、`avatar_zoom`（1〜4）、`avatar_pose_version` を追加。旧画像は中央・等倍。
- 本人用の `PATCH /api/profile-media/:id/position` → `save_my_avatar_position`。画像版と位置版を両方CAS照合する。認証・正規プロフィール一意性・既存試行制限を適用。
- 位置保存はR2へ接続しない。画像キー、画像版、操作履歴、変更成功枠を変更しない。画像GETは既存Blobキャッシュを再利用。
- 数値はAPIとDBの双方で有限・範囲内を検証。DBのNaN/Infinityも拒否。
- 写真変更・削除・所有者変更の既存経路は新トリガーで中央へリセット。画像確定RPCの同一操作ID再試行では位置をリセットしない。
- 応答喪失時はDBから現在の画像版・位置・位置版を再取得して確定を確認する。競合は自動で期待版を更新せず、明示的な再読み込みを案内。
- 大小のアバターは同じ正規化座標・cover計算で描画。保存ピクセル数や画面サイズに依存しない。新画像と位置の両方を保存する場合は画像確定後に位置を保存する。後者のみ失敗した場合は「写真は保存済み・位置は未保存」を表示して再試行する。

## グループの利用順

`get_my_profile_group_usage` はSECURITY INVOKER。本人が作成/参加した、既存RLSで閲覧可能なイベントのみ。開催作成日時が直近90日以内のイベント件数→最終作成日時→グループ名/ID順。独立した開催日や利用日時ログはないため、既存の `created_at` を利用する。

通常/手動・チーム戦・公式戦を別イベントキーで重複排除。チーム戦は代表グループとA/B双方を重複なく集計。欠席のみの登録は出場履歴がある場合に限り参加として扱う。チーム生成時の休憩者もeligible履歴により対象。所属グループ候補は既存の `readMemberGroups` のまま。履歴取得失敗時は名前順で一覧を維持。共通GroupDestinations/ランキングは変更しない。

## 適用手順とガード

1. main・PR head・0049 SHA-256を固定。PRの関連チェック成功を確認。
2. 既存 `cloud-db-backup.yml` をmainで実行。最新の暗号化ファイルをDB外の非公開Draft Releaseへ保管し、別ジョブで実ファイルから復元できたことを照合。
3. `01_preflight.sql` を本番読み取り専用で実行。0048・本人専用RLS/GRANT・参照元テーブル・0049未適用を確認。
4. `profile-avatar-position-release.yml` の `210隔離検証` ラベルで実ファイルを取得・照合・復号し、ネットワーク切断したSupabase PostgreSQL17へ復元。全旧データ、権限、参照関係を照合。
5. 隔離DBに0049適用。`02_verify.sql` と `03_smoke.sql`、旧データ/カタログ不変、追加部分だけの取り消し・再適用を確認。
6. `210本番0049適用` ラベルでは同じ検証を再実行した後、承認済みの0049と履歴のみを1トランザクションで適用。事前固定値から旧データ/カタログが変化した場合は適用前に停止。秘密情報/個人情報/座標値はログへ出さない。
7. 事後のカタログ・旧データ・RLS/GRANT照合。専用一時プロフィールだけを使うスモークは全書込みをROLLBACK。本番の既存プロフィールや画像は変更しない。
8. 通常のSquash merge後、既存のCloudflare自動デプロイとHTTP表示・未認証拒否を確認。ブラウザ操作/撮影は実施しない。

旧データ照合では0049の履歴1行と新しい位置4項目のみを除外する。既存画像参照・版・Instagram・更新日時・画像操作/成功枠を含む元の全列と他テーブルの値は一致必須。既存関数/RLS/GRANTも一致必須。

## 復旧

- 適用中のエラーはトランザクション全体をROLLBACK。応答喪失の場合は再適用せず状態を保全し、履歴/関数/列を読み取り照合する。
- 本番適用後はDBを自動的に戻さない。新UIに問題があれば、まず直前のアプリを通常のレビュー手順で切り戻す。0049は旧クライアントと互換であり、位置設定はそのまま保持できる。
- `isolated_rollback()` は隔離DBでのみ検証。位置設定を保存した本番で列を削除すると設定を失うため、本番では自動実行しない。
- 暗号化バックアップは既存の保管・復元ガードを維持。秘密鍵・実データはPR/公開ログに含めない。

## UIの確認

ユーザー指定によりPlaywright・スクリーンショット・端末別E2Eは実施しない。手動確認はプロフィール統合/鉛筆/写真サブ画面/ドラッグ/ズーム/再ログイン/別端末/画像変更削除/Instagram/利用順/通知内の連携申請を対象とする。

## 隔離復元照合の停止原因（2026-11-17）

0048のInstagram CHECK制約にある `length(...) BETWEEN 1 AND 30 AND ...` は、PostgreSQL内部では入れ子のANDとして保持される。pg_dumpの展開済みDDLを再解析するとANDが平坦化され、意味・検証済み状態は同じでも `pg_get_constraintdef` の括弧が異なり、厳密照合が停止した。差分はこの1制約だけで、旧データ・RLS・GRANT・関数定義は一致していた。

バックアップ復元処理は、ネットワーク隔離された `LocalRestore` に限り、実バックアップの元定義と復元先定義がこの既知の2表記に完全一致する場合だけ、0048の元のBETWEEN構文で制約を再作成する。再作成後は制約を含むカタログ全体を従来どおり完全一致で照合する。未知の表記、不正/未検証制約、本番接続先は拒否する。本番の制約・RLS・GRANTは変更せず、照合項目の無視や一般的な括弧除去も行わない。
