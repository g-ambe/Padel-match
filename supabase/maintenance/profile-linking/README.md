# 本人承認による選手プロフィール連携・統合

本番DBへ自動適用する処理はありません。0039とこのディレクトリのSQLは、Supabase SQL Editorの管理者が手動実行します。CloudflareへのデプロイだけではDBは変わりません。既存の選手・無効化行・以前の修復記録を一括で統合・削除しません。

## 所有するプロフィールと仮登録

有効な `player_profiles.linked_auth_user_id` は、アカウントごとに1行以下に制限します。既存の有効な連携が1行なら、そのIDを引き続き使います。認証ユーザーIDと選手IDが異なる場合も置き換えません。複数の有効な連携がある場合は、作成日・名前・参照数で選ばず、0039を全体ロールバックして具体的なIDを報告します。本人が以前選択したIDを確認し、別途承認された復旧計画が必要です。

新しい本人プロフィールは、アカウント登録やプロフィール画面の明示操作から `ensure_my_player_profile` で作ります。表示では作りません。既存の正規プロフィールがあれば再利用し、新規作成はDB内で直列化し、一意索引でも同時作成を防ぎます。

管理者によるメンバー追加は `add_provisional_club_member` に変更します。未連携の仮選手と所属を同じトランザクションで作り、同じ操作IDでの通信再試行は同じ所属を返します。別グループの同名選手は別の仮プロフィールです。名前で同一人物と判断しません。

## 連携申請と加入申請

管理者は本人から確認したメールアドレスの完全一致で登録済みアカウントを確認します。検索は対象グループの管理者に限定し、10分20回までです。メール一覧や部分一致検索は提供せず、アカウント名と識別番号を返します。`profiles.email` は匿名・一般ユーザー・グループ管理者の直接SELECTから外します。公開共有ページ等が使うアカウント名の列は読み取りを維持します。

管理者の申請は `player_profile_link_requests` と本人通知だけを作ります。プロフィール・所属・戦績は変わりません。本人は申請元、仮登録選手の詳細、全所属と役職・在籍状態・登録日、参加・通常試合・試合結果・チーム戦・公式戦の件数、統合先の名前を確認します。内容への同意後、本人だけが承認できます。正規プロフィールがなければ本人がプロフィール画面で作成してから、申請画面を再読み込みします。拒否・取消・期限切れは統合しません。

加入申請では、仮選手を選ぶと同じ確認内容への同意を求めます。選手ID、確認時の全関連行のスナップショット、同意日時を加入申請へ保存します。管理者承認時にその選手へ統合するので本人の二重承認は不要です。対象を変更する操作は提供せず、DBで直接変更できません。対象選手を指定しなければ本人の正規プロフィールで所属を作り、仮選手には触れません。旧加入申請のうち対象選手ありの申請には新仕様の同意がないため、拒否・取消後に本人が再確認して再申請します。

両申請は `pending / approved / rejected / cancelled / expired` を扱います。期限は作成から7日です。表示は期限を過ぎたpendingをexpiredとして扱い、審査・新しい申請の処理でも期限切れを確定します。定期ジョブを必要とせず、期限を過ぎた行から統合する経路はありません。本人は通知・プロフィール画面、管理者はグループ画面で状態を確認・取消できます。

## 原子的な統合と監査

承認RPCはアカウント・対象メンバー・正規ID・権限・期限を再確認します。管理者発の申請では画面の確認トークンと最新内容を照合します。加入申請では本人が同意したスナップショットと承認時の内容を照合します。申請中に新しい試合や所属などが増えた場合も、古い確認のまま統合せず再確認を求めます。

申請の更新と統合は同じDBトランザクションで実行し、申請操作をアドバイザリロックで直列化します。関連表を決まった順序でロックして、競合検査後の新しい参照を防ぎます。ロックは短時間を想定し、アプリの書き込みと競合すれば通信エラーを成功として表示せず再試行します。

以下を検査し、競合があれば部分統合も監査の部分作成も残しません。

- 同一グループの複数所属（退会・休止も含む）、同一イベントの複数参加。
- 通常試合の選手枠、フレンドリーチーム戦の4枠、公式戦の2枠の重複。
- 統合元の連携済み・無効状態、正規プロフィールの曖昧さ、申請元の権限喪失。
- 旧 `profile_id` と連携先アカウントの不整合、未確認の選手FK。

所属・参加・加入申請・チーム戦4列・公式戦2列の選手参照だけを変更します。`match_players.participant_id`、試合・参加者・イベント・所属の行ID、役職・状態・日時、得点、勝敗、動画URLは維持します。旧 `profile_id` は認証側のIDなので付け替えません。本人の表示名・自己紹介・レベル・利き手・ポジション・地域は、空欄も含めて本人の値を維持します。

元の仮プロフィールは詳細を保ったまま連携なし・無効にし、物理削除しません。通常一覧から外し、参照追加をトリガーで拒否します。監査は `player_profile_merges` に元・先、グループ、申請・承認者、日時、列ごとの変更件数を記録します。変更行のbefore/afterは非公開スキーマ `profile_link_private.merge_changes` に保存します。申請と監査内の元ID・本人の同意記録は歴史情報として付け替えません。未知のFKが追加された場合は意味を確認するまで統合を停止します。

RLSと列権限によって通常ユーザー・管理者による直接連携、解除、無効化、申請改ざんを閉じます。所有プロフィールの表示名・詳細は本人だけが編集できます。管理者は未連携選手の名前・情報と所属の役職・在籍状態を管理できます。管理者の退会・復帰操作は所属の状態変更のままで、本人との連携は外しません。権限判定を守るため、`app_admins` の直接書き換え、所属の旧IDの書き換え、グループ所有者の変更も禁止します。既存 `is_super_user()` の定義は変更しません。

## 手動適用の順序

1. ステージングと本番のバックアップ/PITRを確認し、エクスポートをDB外にも保管します。個人情報が含まれるため一般公開しません。
2. [01_preflight.sql](01_preflight.sql) をSQL Editorの管理者で実行します。全選手数・有効数、重複連携、旧ID、全FK・制約・トリガー・RLS・列権限、旧申請を確認します。RLSで見えるRESTコピーだけで適用可否を決めません。
3. プロフィール・所属・申請・試合等の編集を停止し、[02_backup.sql](02_backup.sql) を実行します。関連データと制約・索引・関数・ポリシー・ACLを同一時点で専用スキーマへ保存します。既存スキーマがあれば上書きせず中止します。日時名を変える場合は03の参照も揃えます。DB内バックアップは外部バックアップの代わりにはなりません。
4. ステージングでは [0039_player_profile_consent_linking.sql](../../migrations/0039_player_profile_consent_linking.sql) の末尾COMMITだけをROLLBACKにしたコピーで試します。内容が問題なければステージングにCOMMITして、本人・管理者・一般ユーザー・匿名の各権限で新規登録、連携・拒否・取消・期限切れ・同時承認・競合を確認します。DDLの試行であっても本番では自動実行しません。
5. 本番への適用内容を確認後、0039をSQL Editorで手動適用します。既存番号0001〜0038は書き換えません。重複等で失敗した場合はROLLBACKし、検査を外さず調査を続けます。
6. [03_verify.sql](03_verify.sql) を実行し、移行直後は既存選手の新しい作成者列以外に変更がないこと、無権限の実行・更新許可がないことを確認します。
7. 対応するアプリをCloudflareへ反映してから利用を再開します。DB未適用時はRPCエラーで停止します。旧画面からの直接連携へフォールバックしません。デプロイはこの作業では実行しません。
8. 既存の所属・役職、各イベント・参加者ID、フレンドリー・公式戦、得点・動画、個人/ペア/グループ戦績、ログインとsuper_userを確認します。

2026-10-23の開発時のREST再確認では78件・有効24件で、有効な重複連携は見えませんでした。依頼時の77件とは件数が異なるため、上記の管理者SQLで実数と差分を確認してください。今回は実DBへの書き込みや既存データの修復は行っていません。

## 復旧

0039が途中で失敗した場合はトランザクションをROLLBACKします。新しいDDLも含めて未確定の変更を戻せます。COMMIT後は旧画面へ単純に戻すと旧直接更新が拒否されるため、利用を停止して修正を前進適用するか、バックアップを別DBに復元して検証してください。広い旧RLSを無確認で復活させないでください。

誤統合は通常画面から戻しません。最新の外部・DB内バックアップを取得し、監査と本人/管理者の確認を行ってから [04_restore_reviewed_merge.sql](04_restore_reviewed_merge.sql) に監査IDを1件だけ設定し、末尾ROLLBACKのまま試します。統合後に対象行が編集・削除されていたら全体を中止し、新しい値を上書きしません。変更前JSONと一致するよう元プロフィールと参照を戻し、監査に復旧日時・実行者を残します。本人設定は戻しません。統合先に追加された新しい行や、別の統合の記録も消しません。結果を再確認してから管理者が手動COMMITし、検証SQLとアプリで所属・戦績を確認します。

監査対象以外の変更や新しいスキーマが絡む場合は自動復旧せず、別DBへバックアップを復元し、監査を照合して個別の計画を作ります。監査・以前のバックアップは自動削除しません。

## 開発時の検証範囲

`npm test` では実Supabaseへ接続せず、実マイグレーションを一時PostgreSQLへ順に適用し、77件の架空データ、権限を切り替えたRPC・RLS・監査・復旧を検証します。PGliteではUUID用拡張のみ標準UUID生成に置き換えます。SDKのHTTP回帰テストでは取得失敗時の増殖防止、保存0件・再取得失敗の拒否を維持します。TypeScript、Next.jsビルド、OpenNextのCloudflare Worker生成も確認します。本番アカウントでの操作・本番マイグレーションの適用結果とは区別してください。

開発環境のローカルPostgreSQL 18.4でも、別接続の同時承認・同時作成、承認中の履歴追加、統合と新規参照の競合の4ケースを検証しています。モバイル幅390pxのブラウザではSupabase応答を置き換え、管理者の申請・本人承認/拒否・期限切れ・明示プロフィール作成・加入時同意を操作確認しました。実DBへの書き込みは行っていません。
