# TASK-01 本人用プロフィール・R2

対象は既存Worker `padel-match`、アカウント `72e845fed80700b737e7e611908c7a6b`、Supabase `padel-hub`（`ntczrmvffmpjzilfebyi`）のみ。課金設定・別Worker・Cloudflare Images・Queues・追加Cron・公開ドメインを作成しません。

## 非公開データと権限

既存 `player_profiles` は他画面でも取得されるため、Instagram/画像参照を公開列へ加えません。1対1の `player_profile_private` を本人限定RLSで関連付け、既存のSELECT/GRANT・選手ID・戦績・プロフィール連携RPCを維持します。画像/Instagram更新は「有効な本人連携が1件」に限定。複数連携時の警告・選択・既存の正規プロフィール特定制約は継続します。

R2は非公開Standard専用バケット `padel-match-profile-images`、Binding `PROFILE_IMAGES`。画像はBearer認証を検証するAPIからのみ取得し、R2管理キーやr2.dev URLをブラウザへ渡しません。連携解除・無効化・所有者変更時の新トリガーは新しい本人用情報のみを切り離し、前所有者のInstagram/画像を新所有者へ渡しません。

## 差替えと復旧

ブラウザでCanvasへ描き直し、最大辺512px・縦横比維持・WebPへ変換（100KiB目標、204800bytes上限）。CanvasのsRGB ICCPも含めEXIF/XMP/不要メタデータを除去します。サーバーはMIMEに加えてRIFF長・WebPチャンク・VP8/VP8Lフレームヘッダー・寸法・容量を検査し、メタデータ/アニメーション/不明チャンクを拒否します。サーバーで画素の完全デコードは行いません。

1. IPのWorkers RateLimit（10回/60秒、POP内近似）と、DBの認証アカウント単位の10回/10分（厳密）を適用。不正な本文/プロフィールIDも認証後の試行に計上。
2. アカウントロック→本人の選手行ロック→現在の画像版と参照・成功回数を検査し、15分のリースを予約。同一プロフィールの未完了操作は1件。
3. 操作UUIDを含む新キーへ条件付きPUT（`etagDoesNotMatch: '*'`）。同一キーを上書きしません。再試行時だけHEADで容量/保存済みハッシュを確認。
4. 本人・有効状態・単一連携・リース・旧参照・版・成功回数を再検査してDBを原子的に確定。成功のみ24時間3回/30日10回に計上（初回/削除も含む）。認証アカウントとプロフィールの双方で計上するため連携先変更でリセットしません。
5. DB確定後に旧キーを優先して回収。削除失敗は参照を巻き戻さず `garbage/deleting` に残し、再試行可能。

ユーザーのJWTだけでDBの画像参照を偽造できないよう、確定/中止/GCはWorkerだけが保持する256bit秘密値も要求します。DBはそのSHA-256のみを `profile_media_private.settings` に保管し、本人・アクティブ状態の確認も省略しません。service_roleはブラウザ/新APIとも使いません。Instagramの保存と画像版は独立しており、画像処理中の他項目編集を妨げません。

通信断では操作UUIDとDBの実状態を照合します。確定済みなら現在の参照を採用し、未完了なら条件付き中止を試みます。DB状態を読めない場合や中止を確認できない場合は「未確認」とし、画像を推測で削除しません。UIの再確認/再試行は回数を限定した明示操作です。通常のSPA画面移動では共通Providerが圧縮/アップロード状態を保持し、ログアウト/アカウント変更でキャッシュを破棄します。ブラウザ終了・リロード後の再送は保証しません。

未参照のステージング画像は24時間猶予後、次の画像変更に付随するGCで回収します。GCは全プロフィールの現在の参照・未完了操作を検査し、削除権をDBで確保してからR2削除。各要求最大3件に限定し、Workers Freeのサブリクエスト数も抑えます。`deleting` は5分後に再試行できます。利用が止まると猶予後の回収も進まないため、運用時に `cleanup.sql` で滞留数を確認し、必要なら `cleanup.py` で対象件数を読み取り確認し、`cleanup.py --apply` で同じ参照/リース検査を行って最大20件だけ回収します。対象DBの検証済みCA・管理接続と対象アカウントのR2管理トークンが必要です。45日以上の監査を保持した後、削除済みオブジェクト/操作だけを整理します。無期限に必ず自動回収されるとは扱いません。定期実行は追加していないため、滞留の監視と運用実行頻度は本番導入前に確認します。

## 切り戻し

問題時は画像APIへの新規要求を閉じ、正常なアプリ版へ安全に切り戻します。新しい非公開テーブル/監査/画像を自動DROP・全DB復元しません。既存機能は新テーブルを参照しないため、旧アプリで既存の試合・戦績・プロフィール機能を維持できます。DB確定済みの画像を「前の画像」に戻すには、新しい操作として現在の参照・版を再確認し、保存済みの実画像から再登録します。削除済みR2オブジェクトの復旧を保証しません。

## キャッシュ・無料枠の見積り

画像APIは本人確認後に `Cache-Control: private, max-age=300, must-revalidate` と `Vary: Authorization` を返します。画像版ごとにURLを変更し、ETag一致は認可/参照確認後に304（R2 GETなし）。Provider内も画像版ごとにBlobを再利用。グループ・ランキング・カード・結果の一覧では画像APIを呼びません。workers.devのCDN Cache APIには依存しません。

今後、公開/ロック機能を追加する際はAPI/RLS/R2配信の権限と可視性の版を揃え、必要ならキャッシュ寿命を短縮/再検証必須へ変更してください。現仕様でも最大5分のブラウザ内キャッシュがあり、既に取得された画像自体を回収することはできません。第三者への閲覧許可は今回追加していません。

[公式R2料金](https://developers.cloudflare.com/r2/pricing/)のStandard無料枠は10GB-month、Class A 100万/月、Class B 1,000万/月、R2からの転送無料（2026-11-16確認）。100KiB/枚なら約97,000人、上限200KiBなら約48,000人の現画像で10GBへ近づきます。旧画像/未参照画像の滞留分は別です。

例：1,000人が各100KiBを保存、月10回更新なら約0.1GB、PUT約1万回（Class Aの約1%）。月100回ずつキャッシュなし閲覧ならGET約10万回（Class Bの約1%）。失敗・再試行・HEAD・運用操作は別途加算します。10万人/月10更新・100閲覧ならR2の各無料枠に近づきますが、それ以前に[Workers Freeの10万要求/日](https://developers.cloudflare.com/workers/platform/limits/)や既存アプリの使用量が制約になり得ます。画像表示はメタデータ+画像の2要求なので、この仮定だけでも約1.5万人で平均10万要求/日に近づきます。

認証失敗/不正要求もWorkers要求を消費し、RateLimit BindingはPOP内の近似制限です。無料枠に必ず収まる・超過時に課金が必ず自動停止するとは保証しません。追加有料アラートや契約は設定しません。Cloudflare DashboardでR2のStorage/Class A/Class B、Worker `padel-match` の日次要求/エラー/CPUを確認してください。今回の管理トークンにはAnalytics権限を求めていないため、自動予算アラートの設定は未実施です。
