## 実操作への影響

- 一般メンバー：自グループの自動/手動開催で、コート数、終了/再開、終了時刻、集計モード、更新日時を変更できる。名前、説明/メモ、共有設定、論理削除、方式、作成日時などの管理項目は変更できない。
- コート数は次に生成するRoundの面数に関わる。既存試合のコートや組み合わせを移し替える処理は追加しない。
- main_admin/sub_admin、グループなし開催の作成者、既存スーパー管理者：既存の管理UPDATEポリシーを維持。画面に出るボタンとDB権限は同一とは限らず、既存ポリシーの管理者範囲を追加で変更しない。
- 他グループのみ所属、無効所属、所属なし、UIDなし：対象開催のUPDATEは0行。匿名は既存GRANTでも不可。
- 通常開催の作成者が一般メンバーの場合、作成者という理由だけで管理項目を変更可能にはしない。画面の既存判定と合わせる。
- フレンドリーチームマッチ：ホストグループの一般メンバーだけでは管理UPDATEを許可せず、既存の作成者・両側グループ管理者・スーパー管理者の経路を維持する。公式戦official_eventsは対象外。
- 名前・共有設定・開催削除は既存管理者向け。一般メンバーのスコア保存、参加者操作、Round生成、試合削除は前セットの権限を維持する。

実装上、コート数保存はlib/event-courts.tsが現在値を比較してUPDATEし、app/events/[id]/page.tsxの終了/再開はstatus・closed_at・stats_modeをUPDATEする。名前/共有/開催削除も同じevents UPDATEなので、行条件だけで一般メンバーを許可すると管理項目まで書けてしまう。このため今回はフィールドガードを併用する。

## チーム開催の論理削除の補正

既存events_update_friendly_team_match_managersはUSINGだけでなくWITH CHECKにもis_deleted=falseを要求する。そのまま無条件UPDATEを外すと、正当な作成者・側管理者がis_deleted=trueにする画面の削除が失敗する。

WITH CHECKからこの条件だけを外し、team方式、stats_mode/statusの既存の値範囲、can_manage_friendly_team_event_by_sidesは維持する。USINGの旧行is_deleted=falseは維持するため、削除後に側管理者が復元/編集できるようにはしない。この補正もevents UPDATE1操作に含み、追加計上しない。

## 適用後の画面確認案

一般メンバーで確認用の自動開催を使う：
1. コート数を一時的に変更して保存・再読込し、設定が残ることを確認して元に戻す。
2. 開催を終了→再読込し終了状態を確認→再開→再読込し開催中に戻ることを確認する。これにより集計対象への切替と運営再開の両方を確認する。

管理者で同じ確認用開催の名前を一時変更→保存/再読込→元に戻す。
共有設定やフレンドリーチームマッチを普段使っている場合は、確認用開催の共有作成/解除・終了/削除も追加確認する。削除は今回作った確認用開催だけを使い、既存の本番記録では試さない。
