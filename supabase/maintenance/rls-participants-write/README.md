## 実操作と許可範囲

| 操作・ユーザー | 適用後 |
|---|---|
| グループの在籍中の一般メンバー・メイン/サブ管理者 | 自グループ開催へのメンバー自動追加・ゲスト追加、ゲスト名変更、休憩/復帰を許可 |
| 連携済み選手IDで所属するユーザー / 旧profile_idで所属するユーザー | 両方の所属経路を維持 |
| 他グループだけの所属、所属なし、無効所属 | 対象開催へのINSERTを拒否、UPDATEは0行 |
| グループなし開催の作成者 | 自分を参加者にする・ゲスト追加・名前/状態の変更を許可 |
| グループなし開催の他人 | 追加/更新を拒否 |
| スーパー管理者 | 既存is_super_user判定による追加/更新を維持。ただし削除済み開催の参加者は対象外 |
| フレンドリーチームマッチの管理者 | 既存の相手側管理判定も維持。event_team_matches等の実装・権限は無変更 |
| 未ログイン | 既存のテーブル権限でもINSERT/UPDATE不可 |
| 削除済み開催 / 開催なし・存在しない開催 | 追加/更新不可 |
| 終了済み開催 | 現在の詳細表示でもメンバー自動追加が走るため、未削除なら在籍者の操作を維持 |

通常画面では、開催作成後および詳細を開く際にlib/event-participants.tsのaddMissingClubMembersToEventが不足メンバーを一括INSERTする。グループなしはaddCreatorToNoGroupEventが本人をINSERTする。app/events/[id]/page.tsxのゲスト追加はINSERT、ゲスト名編集・休憩/復帰はUPDATE。休憩状態は後続のRound生成が参加候補を選ぶ際にも利用する。

この一連の処理に使う2操作を同じセットで保護する。生成済み試合、スコア、ランキング、公式戦のテーブルは変更しない。共有ページはSELECTの取得先・権限を維持する。

INSERTには参加者側のチェックも設ける。ゲストは選手/アカウント参照なし、メンバーはその開催のグループに在籍する選手（旧IDも含む）だけ。グループなし開催は作成者本人のみ。スーパー管理者のメンバー追加は既存の参照制約・有効選手トリガーを前提に許可する。

UPDATEではID、event_id、profile_id、player_profile_id、participant_typeをWebロールから変更不可にする。通常画面が変更するguest_name/statusは維持する。既存の本人連携のSECURITY DEFINER処理と管理者DBメンテナンスはこのガードの対象外。統合済み/無効選手への新しい参照を拒否する既存guard_referenceも維持する。過去の参加者の休憩状態変更に「現在も選手が有効」という新条件は付けず、過去記録への過剰な制限を避ける。

## SQL・切り戻し・残る範囲

- apply.sql：現行2ポリシーの完全一致を確認。dev_allを削除し、INSERT/UPDATEを制限付きにする。SELECT/DELETEは互換ポリシーに分割して現行の許可範囲を維持。本人連携とは別の非公開スキーマにSECURITY INVOKERトリガーを置き、Webロールの参加者付け替えを止める。補助対策としてanon/authenticatedのTRUNCATEを撤回。
- rollback.sql：適用後ポリシー全定義・新トリガー/関数定義・TRUNCATEの実効拒否が一致するときだけ戻す。元のdev_allとTRUNCATEを復元する。切り戻すと既知の無条件許可も復活する。
- verify.sql：適用前後のRLS、全ポリシー、直接ACL/実効権限、トリガー、本人連携関数、件数、他テーブルのポリシー/ACLハッシュをREAD ONLYで比較。
- どちらもBEGIN/COMMIT、lock_timeout3秒、statement_timeout15秒。同じ表をロックして変更をまとめる。テーブルや行は削除しない。
- 適用直前にはpreflight-verification.jsonと比較し、他工程の変更やACL/grant optionの差異があれば再検討する。新スキーマが既に存在する場合も停止する。

今回の完了対象はINSERT/UPDATEの2項目だけ。SELECT/DELETEの全許可はまだ残る。他グループの閲覧や物理削除まで防止済みとは扱わない。DELETEは現在のUIに見当たらなくても参照関係や連携復旧を調べて別途判断する。TRUNCATEとIDガードは補助対策として分母33へ重複計上しない。

親eventsを先に自グループへ移す攻撃は、本番適用済みのevents_identity_private.guard_event_identityが前提として拒否する。この前提も専用テストに組み込んだ。
