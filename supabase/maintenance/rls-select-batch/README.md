## SELECTの条件と匿名の列権限

eventsは無条件SELECT互換ポリシーを削除する。既存の所属・グループなし本人・スーパー管理者のSELECTを維持する。
公開共有用SELECTには既存の終了/共有ON/未削除/トークン非NULL条件に加え、request.headersのx-padel-share-tokenとの一致・空トークン禁止を加える。authenticated向けに共有の無条件例外は追加しない。
event_participants/rounds/matchesはRLSで読める親eventsの存在を要求し、match_players/match_resultsはRLSで読める親matchesの存在を要求する。この順序で循環参照を作らない。

匿名は6表のテーブル単位SELECTを外し、anonymous-columns.jsonにある共有画面の取得・フィルター・埋込みに必要な列だけを許可する。イベントの内部説明/メモ/作成者参照等は匿名SELECT不可。匿名SELECT *は意図的に42501となる。通常のauthenticatedとservice_roleのSELECT権限は変えない。
他表のプロフィール情報を無条件に追加公開するGRANTは行わない。

## チーム開催で必要な補正

### 退会済み作成者

既存public.can_view_friendly_team_event_by_sidesは作成者なら所属終了後もtrueだった。既存関数の作成者分岐を、現在もホストグループへ在籍している場合、またはグループなし開催の場合へ絞る。作成者引数だけでなく実際のevents.created_by_auth_user_idも照合する。
既存の側グループの在籍者・スーパー管理者の分岐、関数の署名・所有者・既存ACLは維持する。新しいSECURITY DEFINER関数は作らない。
既存関数内でeventsを参照するため、実行所有者がRLSをバイパスできることを事前ガードで必須にし、合成DBでも再帰がないことを検証する。

### 論理削除に必要な行の可視性

正当な側管理者がis_deleted=trueへ更新した後の行がSELECT不可だと、論理削除自体が42501で止まることを実SQLで確認した。
events_select_friendly_team_match_viewersを、通常は未削除、削除済みは現在の正当なチーム管理者が読める条件へ補正する。can_viewとcan_manageの両方を要求し、退会済み作成者には開かない。既存のUPDATE USINGは変更しないため、側管理者の削除後復元まで開放しない。
ホストグループ在籍者が既存events_selectで読める範囲やスーパー管理者権限は維持する。

### 閲覧認可の迂回防止

event_team_sides_manageとevent_team_matches_manageはFOR ALLのWITH CHECKがtrueだった。補助修正なしの状態を合成DBで再現すると、他グループの開催に自グループをsideとしてINSERTし、そこから閲覧権限を作れることを実証した（本番には試していない）。

2つのWITH CHECKを、実在する未削除・開催中のチーム開催で、既存can_manage_friendly_team_event_by_sidesが認める作成者/グループ管理者/スーパー管理者である条件へ置換する。INSERTと、UPDATE後の移動先の両方を認可する。
既存USING・ロール・GRANTは変更しない。既存USINGによる既存行の編集/削除範囲を別途広げる変更ではない。相手側管理者による既存カード編集など、もともとUSINGで通らない画面操作の調整は本件へ混ぜない。

## SQL・切り戻し・検証SQL

apply.sql：
- 主6表と補助2表を一定順序でロック。全ポリシー/直接ACLと、対象6表に既存の列GRANTがないこと、8表のRLS有効、既存の閲覧関数定義/実行所有者を確認する。

- テーブル/制約/行の追加・削除・修復・統計再計算はしない。既存の書込みRLSを削除/無効化しない。補助2表のWITH CHECKだけは上述の理由で変更する。

rollback.sql：
- 適用後のポリシー・直接ACL・列ACL・閲覧関数定義が期待と完全一致するときだけ戻す。
- 新しいSELECTと匿名列GRANTを外し、元のSELECT/テーブルGRANT・関数・チームポリシーを復元する。元の無条件閲覧や広いチーム追加許可も戻るため、障害時の一時復旧として使う。
- PostgreSQLの列REVOKEは空ACL配列を残す場合がある。空配列とNULLは実効権限が同じなので、aclexplodeで規格化して比較する。実効権限の復元と再適用まで確認済み。

両SQLはBEGIN/COMMIT、lock_timeout3秒、statement_timeout15秒。途中コミットなし。
verify.sqlで8表の件数/RLS/ポリシー/テーブルACL、主6表の列ACL/列別SELECT可否、実効権限、既存トリガー、認可/本人連携関数、制約、他表のACL/ポリシーをREAD ONLYで比較する。
本番に試し書き、DELETE/UPDATE→ROLLBACKテスト、実在他人データでの攻撃試験は行わない。
