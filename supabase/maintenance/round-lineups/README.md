# Roundメンバー変更：手動適用・停止・復旧

**PRはDraft・未マージ。本番SQL・マージ・デプロイはこの作業では実行しない。** 新Migrationは `0041_atomic_round_lineups.sql`。0040を含む既存Migrationは書き換えない。コード設計・制約・試験は [docs/round-lineup.md](../../../docs/round-lineup.md) を参照。

## 本番適用前の判断

- 利用者がDB設計・新RPC・旧クライアントの制限・本手順を承認する。
- 本番の最新カタログは未取得。`01_preflight.sql` の結果と現在のRLS・列権限・トリガー・0040を照合する。開発試験はリポジトリに保存された本番適用記録の再現であり、現時点の本番一致を保証しない。
- 重複結果・不完全カード・同じRoundの二重出場があれば対象IDを調査する。自動削除・統合・既存制約の緩和をしない。新RPCは不整合な対象を拒否する。
- 固定使用履歴のあるRoundは編集不可とする方針を確認する。固定0組の既知の履歴だけ出場者を更新する。不明な過去の参加機会を推測しない。
- 監査を持つ通常イベントは物理DELETEを参照制約で拒否する。既存画面の論理削除は維持し、監査消失や開催ID再利用を防ぐ。将来の物理削除・保管期限は別途レビューする。
- 新画面を反映する前に0041が必要。未適用時の旧保存への自動フォールバックはない。手動作成・チーム・公式の保存経路は維持する。

## SQLとアプリの順序

1. 操作を止める時間帯を確保し、`01_preflight.sql`（SELECTのみ）の結果をレビューする。
2. `02_backup.sql` で同一DB内の一貫したコピーを作る。スキーマが既存なら停止し、上書きしない。
3. **DB外へ論理バックアップを取得し、別の保管先に保存する。実ファイルの隔離復元・照合を完了してから進む。** 下記参照。
4. 0041全体をSQL Editorで手動適用する。1トランザクション、ロック待ち5秒、実行60秒。タイムアウトなら全体失敗として原因を確認し、断片を実行しない。
5. `03_verify.sql` でRPC・権限・追加ガード・行の整合性を検証する。`editing_enabled=false` が初期状態。既存行との差分があれば調査し、バックアップで一括上書きしない。
6. 隔離環境で新画面・RPCを試験し、利用者が別途マージを承認する。その後、既存の自動デプロイで新アプリを反映する。
7. 入替をまだ無効のまま、テスト用イベントで構成付きスコア保存・修正・生成・終了を確認する。旧タブは再読み込みする。
8. 利用者承認後に `05_enable.sql` を手動実行して入替を有効にする。ページ再読込後に「メンバー変更」が表示される。
9. テスト用イベントで同コート・別コート・休憩交代、取消、スコア済み拒否、他端末、固定使用済み拒否を確認する。実試合データで破壊的試験をしない。

SQLを適用しただけでは入替は有効にならない。CloudflareデプロイだけではSQLは適用されない。

## DB外バックアップと復元確認

Supabase Freeの自動日次バックアップを前提にしない。同一DB内コピーだけではDB障害・誤操作に備えられない。

[既存のDB外バックアップ手順](../event-fixed-pairs/README.md)を利用できる。Supabase CLIの `db dump`、または接続先に対応する `pg_dump` でスキーマ・データ・必要な権限情報を取得する。CLI標準dumpが除外するauth/storage等と、publicからの外部キー参照先も確認する。接続先DBバージョン以上の対応クライアントを使用する。

例えば接続情報を安全な環境変数へ設定したクラウド端末で、Git外の専用ディレクトリへcustom形式を取得する。以下は**手順例であり実行済みではない**。

```sh
# 接続文字列やパスワードをチャット・ログ・Gitへ書かない。set -xを使わない。
pg_dump --format=custom --no-owner --file=/private-backups/padel-before-0041.dump "$SUPABASE_DB_URL"
pg_restore --list /private-backups/padel-before-0041.dump > /private-backups/padel-before-0041.list
```

- 作成されたファイルのサイズ・SHA-256・取得日時・対象プロジェクトを記録し、暗号化してGit外の別保管先へコピーする。復号鍵はDBパスワードと別に保管する。
- `pg_restore --list` は復元成功の証明ではない。**保管先から実際に取り出したファイル**を、同等のロール・拡張・authスキーマを備えた隔離Supabase/PostgreSQLへ `pg_restore --exit-on-error` 等で復元する。
- 本番接続先を復元先に指定しない。イベント・Round・参加者・出場者・結果・固定設定／監査の件数、外部キー、代表的な履歴・動画・結果を照合する。失敗したら適用を停止する。
- 本番データを含むdump、復号済みファイル、接続情報、鍵をリポジトリへ置かない。試験環境もアクセスを限定し、終了後に適切に破棄する。

## 旧クライアントとの互換性

- 0041適用後も、入替していないイベントでは旧生成・旧スコア保存を維持する。旧スコアの二重INSERTは追加ガードで拒否する。
- 入替済みRoundでは旧 `match_results` INSERT/UPDATE・`matches.completed` 更新・旧構成INSERT/UPDATEを拒否する。旧クライアントは最新画面へ更新する必要がある。
- 入替済みイベントでは旧直接Round INSERTと旧 `create_fixed_pair_round` を拒否する。旧RPC本体は非公開へ移し、新RPCだけが履歴取得前の版数を検証して呼ぶ。旧方式のGUCによる解除経路は設けない。
- 新スコアRPCは入替の有効化前も使用できる。入替停止後も、既に変更したRoundのスコアを安全に保存するため維持する。
- 既存の削除・動画・共有・手動編成は維持する。旧複数リクエスト削除との競合ではDBのデッドロック検出等で一方が安全に失敗する場合がある。エラー後に再取得し、削除を自動継続しない。

## 切り戻し・データ復旧

1. 問題時は `04_disable.sql` で**新規入替だけ**を停止する。新スコア・新生成RPC、旧保存拒否ガード、版数・監査は残す。
2. 可能なら対応済み画面を維持して修正する。旧Workerへ戻す場合、入替済みRoundの旧スコア保存・旧生成は拒否されたままとなる。可用性の制約を確認してから戻す。
3. 誤った入替は監査の `before_state`／`result`／`changed_rows` で対象を確認する。バックアップ全体を本番へ上書きしない。
4. `06_recover_reviewed.sql` は個別承認用テンプレート。承認した元要求ID・担当者アカウントIDが未設定なら停止し、末尾はROLLBACKのまま。以後の履歴・スコア・状態が変わっていれば停止する。
5. テンプレートは元の検証付きRPCを使って**新しい入替として**復旧する。版数・固定利用済み印・元監査は巻き戻さない。担当者の既存開催操作権限も検証する。一時有効化はそのトランザクション内だけで外部へ公開しない。
6. 復旧プレビューと新旧要求IDを確認し、利用者の承認後にだけCOMMITを検討する。スコア済み・固定使用済み・参加者状態変更などで拒否されたケースは別途調査する。保護を削除して強行しない。

0041のDROPや元RPCへの無条件復帰は通常の切り戻し手順に含めない。監査・版数・旧クライアント拒否を消すと古いスコアを誤った選手へ保存できるため。
