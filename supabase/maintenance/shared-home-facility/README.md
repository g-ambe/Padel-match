# ホームコート共通施設ID（0051・作業中）

## 現在の状態

- 実装・合成データによる軽量検証のみ。本番適用・マージはしていない。
- 全国施設の出典確認が未完了。施設追加・名称/都道府県の修正SQLはまだ含めない。
- 本番の既存9施設をSELECTで確認した。個人の既存自由入力を勝手に施設IDへ変換しない。
- 0051は既存施設の行・ID・クラブ参照を変更しない。閉業施設も削除しない。

## 施設データの正本と登録条件

正本は日本パデル協会の公式コート一覧 https://www.japanpadel.com/court-list/ のみ。
施設名・都道府県・所在地・新規掲載対象は原則として協会情報を優先する。
第三者サイトは補助資料に限定し、協会未掲載の施設を第三者情報だけで自動追加しない。
協会掲載と営業中の確認は区別し、閉業・休業情報と矛盾する場合は施設公式情報等で追加確認する。
未確定の候補はデータMigrationから除外して保留する。

協会に未掲載の既存施設も確認なく削除・無効化・統合しない。
施設ID、クラブ参照、個人のホームコートIDと自由入力を保護する。
照合記録と根拠は `docs/facility-master-review-2026-11-17.md` に集約する。
全国施設の差分照合と0051の安全確認が完了するまではPR #212をDraft・未マージに保つ。

## 保存と互換性

個人は `player_profile_private.home_facility_id`（任意FK、削除RESTRICT）から、
グループは従来の `clubs.main_facility_id` から同じ `padel_facilities.id` を参照する。
表示名はマスターを参照する。既存 `home_court_name` は自由入力、または施設選択時点の
名称スナップショットとして残す。改称時にIDを差し替えない。

新RPC `save_my_home_court_selection` は0050と同じ本人判定、唯一の有効な連携、
チケット消費、`home_court_version` によるCASを使う。本人確認の親行ロックを再利用する。
通常のSELECTは既存RLSに従い、認証ユーザーへの直接UPDATE権限や第三者の閲覧権限は追加しない。
旧RPCの自由入力保存は施設IDを解除する。連携所有者変更時も名前・IDを一緒に解除する。
Instagram、画像、位置の版や成功回数枠は変更しない。

施設マスターの追加メタデータは、安定キー（名称とは別の一意キー）、別名、営業/利用条件、
利用上の注記、確認日。現在の9施設は未確認扱いで保持する。将来の確認済みデータSQLでは
既存IDに安定キーを割り当て、同じキーの再実行で施設が増えない方式にする。
名称や別名が複数IDに一致する場合は自動統合せず停止する。

   掲載と営業中を同一視せず、閉業・休業情報との矛盾は施設公式情報等で確認し、未確定は保留する。
   第三者情報だけの新規追加、協会未掲載を理由にした既存施設の削除・参照解除は禁止する。
   採番はその時点のmain・未マージPRで再確認する。過去の0016は編集しない。
2. main/PR head/各Migration SHA-256を固定する。0050適用済み、0051未適用、同名RPCなし、
   想定FK/関数/RLS/GRANT/既存データを読み取り専用で照合する。
3. mainの既存 `cloud-db-backup.yml` から最新暗号化バックアップを取得する。
   古い実行のバックアップやローカルの弱いパスフレーズで代用しない。
4. 実バックアップファイルを取得・ハッシュ照合し、ネットワークを切り離したSupabaseへ復元する。
   `event-fixed-pairs/cloud_backup.py` の既存復元/カタログ照合を再利用し、データ・FK・RLS・ACLを確認する。
5. 0051と確認済みデータSQLを隔離DBに適用する。`02_verify.sql` と既存0050検証SQL、関連試験を実行する。
   既存9IDがすべて残り、全クラブの `main_facility_id` と全個人のホームコートID/文字列が完全一致することを照合する。
   施設行の差分は根拠一覧にある補正・追加だけ許可する。データSQLの再実行で追加件数が増えないことも確認する。
6. 専用テストデータで本人/他人/匿名/複数連携、ID/自由入力/解除、CAS、試行制限、旧RPC互換を確認する。
   既存の本番プロフィールへ試験書込みしない。隔離環境でのみ復旧リハーサルする。
7. 最終SHA/ハッシュ/新鮮なバックアップを再照合した専用ガードを整備してから本番適用する。
   過去PR番号・Migrationに固定された0050リリースワークフローを0051に流用実行しない。
8. 本番検証成功後にのみアプリをマージする（新アプリは0051のFK/列/RPCを前提にする）。
   既存の自動デプロイを使用し、プロフィール読取と権限のある専用プロフィールで確認する。

## 復旧

旧アプリは0051適用後も従来の自由入力RPCで動くため、アプリ切戻しを優先する。
位置・画像・Instagramの保存方式はそのまま。施設IDの選択内容を保存した後に、列削除や
本番バックアップ復元を自動実行してはいけない。DBは保全し、原因と影響を確認する。
DDL適用はトランザクション内、失敗時は未確定のDDLをロールバックする。
実データ復元と復旧可能性を確認するまではDraftを解除しない。
