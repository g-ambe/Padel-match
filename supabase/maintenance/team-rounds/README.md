# フレンドリーチーム戦の乱数ラウンド（0045）

2026-11-10の条件付き承認に基づき、以下の本番安全確認がすべて成功した場合のみ0045適用・Squash merge・既存自動デプロイへ進める。0045は0044適用済み環境用。既存Migrationを書き換えない。通常フレンドリー・公式戦は対象外。

## データと権限

- `event_team_rounds`：開催ごとのラウンド番号、モード、生成面数、確定時の参加可能者スナップショット、操作UUIDと要求の指紋を保持する。
- `event_team_matches`：`round_id`・`round_number`・`court_number`・`generation_mode`、各選手枠の`*_source_side`・`*_guest_id`を追加する。既存の4選手FK・対決スコア・メモ・動画は維持し、混合専用の`pair_1_score`・`pair_2_score`・`pair_result`を追加する。
- 自動編成の既存選手枠`team_a_player*`がペア1、`team_b_player*`がペア2を表す。元所属は別の`source_side`から判断し、カラム名で推測しない。対決の得点は従来欄、混合は専用のペア得点欄に保存する。混合の従来`team_a_score/team_b_score`は常にNULL・従来`result`はundecidedとなるCHECK制約を設け、古い画面が混合結果をチーム勝敗へ誤加算することも防ぐ。旧画面には未入力として見えるため、混合の正しい結果確認には画面更新が必要。
- 既存カードの追加列はNULLのまま。`round_id=NULL`は従来の手動対決として扱い、元所属は従来どおり先頭2枠=A・後半2枠=B。過去データを変換しない。
- 新テーブルはRLS有効、閲覧は既存の開催閲覧権限に従う。直接のINSERT/UPDATE/DELETEを付与せず、匿名の新RPC実行を拒否する。既存テーブルのRLS・GRANTは変更しない。
- 新RPCの操作権限は0044と同じ`can_manage_friendly_team_event_by_sides`と`can_view_friendly_team_event_by_sides`の両方を検証する。作成者・対象チーム管理者・既存super権限の条件を流用し、一般メンバーへ拡大しない。
- 0044の出欠RPCをCREATE OR REPLACEし、未完了カードの確認を「元所属＋プロフィールID／ゲストID」で行う。旧カードの名前参照にも互換対応する。既存の欠席拒否・所属ロックを維持する。

## 保存・競合

1. `get_friendly_team_round_context`が現在の有資格者・全カード・ラウンド履歴と指紋を返す。欠席者・無効な選手・非在籍者は候補から除外する。
2. クライアントは純粋関数でプレビューする。この時点ではカード・ラウンド・コート数を保存しない。
3. `create_friendly_team_round`は開催をロックし、参加資格・履歴の指紋、未完了カード、ペア構成、全コートの重複出場を検証する。所属・選手・ゲストをSHAREロックし、複数面とコート数を1トランザクションで確定する。
4. 同じ操作UUID・同じ要求の再送は保存済みラウンドを返す。別内容への使い回しは拒否する。応答喪失時も編成とUUIDを保持する。再抽選時だけ新しい要求にする。
5. 手動カードの書込みも開催ロックに参加する。自動編成の未完了カードと同じ選手を手動カードへ追加・入替することを拒否する。手動カードが未完了なら新ラウンドを生成しない。
6. 自動編成カードの編集・スコア・動画・メモは`update_friendly_team_round_card`で元行の期待値を照合する。競合は更新を拒否し、ScoreSaveProviderの入力・再試行を保持する。既存ScoreInputには表示用のペア得点を渡し、混合の保存RPCだけが専用欄へ変換する。同じ更新の応答喪失後の再送は、既に同じ結果なら再更新せず成功を返す。
7. 自動編成カードの削除は期待値付きRPCを使用する。古いクライアントの直接更新・削除は「画面を更新して操作してください」と拒否する。既存の手動カードの保存経路は維持する。
8. 自動カードの編成変更は元所属を固定し、有資格者・全ラウンドの重複をDB側でも確認する。未登録の自由入力ゲストは、既存のイベントゲストテーブルへ同じ所属で登録して安定IDを与える。スコア・動画だけの変更では過去の在籍や欠席状態を再解釈しない。

プロフィール統合用の既存4選手FKをそのまま使う。未確認の新しい選手FKを増やさず、`check_reference_schema()`が成功する。プロフィール統合によって同じラウンド内の重複出場になる場合は、遅延整合性検査で全体を拒否する。履歴の参加資格スナップショットを推測で書き換えない。

## 公平性と集計

- 生成面数は設定1～5面・各チーム人数/2・重複を除いた総人数/4の最小値。同じプロフィールの両所属にも、2チームの定員を同時に満たす動的計画法で対応する。
- 出場回数が少ないこと、連続休憩、累計休憩の順で優先する。公平性の同条件は乱数で選ぶ。ペア・相手の連続、累計回数を順に評価し、有効な編成を256通り試行する。全員に実スコア履歴があるコートのみ、既存の戦績評価関数で最後に実力差を考慮する。実力は補完しない。
- 手動カード・自動カードとも保存済みの編成を出場・ペア・相手履歴へ使う。休憩は、有資格者スナップショットと全コートが残っている新ラウンドだけから評価する。手動時代・途中参加前・欠席中・削除済みコート・統合前IDの不明な休憩を推測しない。
- 自動休憩で出欠を変更しない。両所属でも他方のチームから実際に出場していれば、同一人物を「休憩」と重複計上しない。
- 対決は従来のチーム・個人・ペア戦績へ、混合は個人・ペアのみへ加算する。既存の勝点、0-0除外、得失点、順位・表示タイミングは維持する。
- イベントの終了・再開・`stats_mode`は既存処理のまま。現在のグループ年間ランキングは通常フレンドリーの`matches/match_players/match_results`を読む実装で、従来の手動チーム戦と同様、本テーブルを新たに年間集計へ取り込まない。イベント内の個人・ペア戦績と独立ランキングの新規開発を混同しない。
- 混合を旧クライアントのA/B集計へ渡さないため、DB適用→新アプリ反映→専用テスト開催で確認→運用開始の順を守る。反映前に自動生成を使わない。

## 承認後の本番適用順序

SQLをユーザーが手動実行する必要はない。Codexが条件付き承認の範囲内で、承認済み手順を行う。

1. 最新main・PR SHA・0045のSHA-256を固定する。最新本番カタログを`01_preflight.sql`で読み取り専用確認し、隔離試験の前提と比較する。差異があれば停止する。
2. [既存のDB外バックアップ手順](../event-fixed-pairs/README.md)と[既存クラウドバックアップ](../../../.github/workflows/cloud-db-backup.yml)を再利用する。同一DB内コピーのみで済ませない。暗号化dumpを非公開に保管し、チェックサム、同じ実ファイルの隔離復元、データ・RLS・ACL・参照関係を確認する。秘密値・平文dump・実データをGitへ追加しない。
3. その最新復元DBで0045、関連テスト、既存データ不変、`02_verify.sql`、復旧を再確認する。0044は適用済みであること。既存手動カード・通常フレンドリー・公式戦の件数と既存列の内容を照合する。
4. 承認された0045のみを、管理用接続・ON_ERROR_STOP・Migration内のBEGIN/COMMITで原子的に適用する。予期しない変更があれば後続を停止する。既存Migration管理台帳の運用に従い0045の適用を記録する。
5. `02_verify.sql`の期待値、既存RLS/ACL、既存データ・通常戦績・プロフィール参照を比較する。確認失敗時はマージしない。
6. PRをSquash mergeし、既存Cloudflare自動デプロイを確認する。手動で二重デプロイしない。非必須ステージングの既存問題は既存承認済み運用に従い、必須チェックは迂回しない。
7. 専用テスト開催だけで両モードの生成・再抽選・保存・スコア・出欠・終了・戦績分離・共有を確認する。既存の本番試合は変更しない。

## 障害時の復旧

- まず`03_disable_generation.sql`で新規生成だけを停止する。既存ラウンド・スコア・履歴・更新RPCは保持する。設定やRLSを緩和しない。
- 生成データが0件の場合だけ、`04_rollback_empty.sql`によるDB切戻しを検討できる。既定はROLLBACK。承認された隔離検証と本番前確認を経てのみ実行する。0044の出欠RPCを元の定義へ戻し、既存カード・権限は維持する。
- **生成データが1件でもある場合、0045の削除や旧アプリへの単純切戻しは禁止。** 混合データを旧アプリが誤解釈するため、生成停止と互換性を保った前進修正を使う。スコア保存・閲覧用RPCを残す。
- バックアップ復元・生成データ削除は自動実行しない。DB外バックアップから隔離DBへ復元し、適用後の差分・戦績・監査を保全して、別途承認を受けた復旧を行う。

## PR191専用クラウド実行

[専用ワークフロー](../../../.github/workflows/team-rounds-release.yml)は同一リポジトリのPR191・既存ブランチだけを対象にする。バックアップは既存ワークフローで取得し、復元成功した非公開Draft Releaseの暗号化asset IDとSHA-256を固定する。

- `191隔離リハーサル`ラベル：本番は読取り専用preflight／復元カタログ照合のみ。実バックアップを外部通信のないDBへ復元し、0045・旧全行・権限・既存戦績・専用開催・空データ切戻し／再適用を確認する。
- `191本番適用`ラベル：同じ復元試験の成功後、固定main・PR head・SQL／バックアップハッシュを再照合。短時間のpublicテーブルロック内で、バックアップ後の全対象行・カタログの変化を拒否し、0045のみを単一トランザクションで適用・再検証する。更新が入っていた場合はバックアップを更新して再検証し、条件を弱めない。
- `191本番検証`ラベル：マージ後・本番自動反映確認後のみ実行。既存所属は読取りだけ、新しい専用開催をrecord_onlyで作成して手動・対決・混合・得点・再送・戦績分離を確認する。検証後はその開催だけ終了・論理削除し、既存試合やプロフィールへ書き込まない。失敗時は当該テスト状態を保全する。

秘密情報・実データは引数やログに出さず、暗号化バックアップは非公開保管を維持する。復元証明の平文ファイルはジョブ内の一時領域だけに置き、Git・公開artifactへ保存しない。本番適用後のエラーでもDBの削除・バックアップ復元を自動実行しない。

## マージ後の0045適用（2026-11-10の追加承認）

PR191はmain `a061c6c24710ca465487c12e516c8f909abf978a` としてマージ・自動反映済み。`post_merge_apply.py` と既存ワークフローの手動起動を、既存作業ブランチ上で使用する。新規PR・追加のアプリデプロイは不要。マージSHA・元PR head・作業コードSHA・0045ハッシュ・本番自動デプロイ成功を固定照合する。

mainで取得・復元成功した最新の暗号化バックアップのrun／Release／asset ID・SHAを指定し、実ファイルを再び隔離復元する。過去の合成データ・大規模回帰試験は繰り返さない。最新データでの0045互換性・既存戦績・既存RLS／GRANTと、適用中のデータ保全だけを確認する。

前回の停止は、バックアップ取得後の正常な認証・通常試合の更新まで拒否したため。マージ後手順では、その更新を古いバックアップで上書きしない。適用直前の単一REPEATABLE READトランザクションで既存publicテーブルを短時間ロックし、最新の全対象行ハッシュを一時表へ記録する。0045適用後に同じスナップショットの全既存列を照合し、DDLによる行変更・欠損があれば全体を拒否する。バックアップの古い行値との一致を求めず、適用時点の最新データを保持する。追加NULL列の除外は `event_team_matches` だけに限定する。

既存カタログは隔離適用の前後と厳密に照合する。新ガードは、隔離DB内の専用行で「取得後に正常な入力が追加されても保全できる」「適用中の行改変は拒否しROLLBACKする」の両方を確認する。新たな本番テスト開催や大規模試験は、検証省略の指示に従い実行しない。適用後の読取り専用の権限・制約・参照確認は実行する。異常時にDB復元や破壊的な切戻しを自動実行しない。
